> # CapsLock v1.5.0 可控 Skill 开发计划
>
> ## 版本目标
>
> 基于 v1.4.1 的运行时、权限和审计能力，引入本地声明式 Skill。Skill 只能由用户通过 `/skills run` 显式启动，不能自动触发、安装代码、执行任意 Shell 或扩大当前会话权限。
>
> 预计工作量：单人约 12–15 个工作日。
>
> ## 接口与数据契约
>
> Skill 采用目录包：
>
> ```text
> capslock.skills/<skill-name>/
> ├── skill.toml
> ├── instructions.md
> ├── schemas/input.json
> ├── schemas/output.json
> └── fixtures/*.json          # 可选
> ```
>
> `skill.toml` 固定字段：
>
> - `schema_version = 1`
> - `name`、`version`、`description`
> - `min_capslock_version`
> - `instructions`、`input_schema`、`output_schema`
> - `required_tools`
> - `required_permissions`
>
> 规则：
>
> - 名称使用小写字母、数字和连字符，目录名必须与名称一致；版本使用 SemVer。
> - 输入、输出使用 JSON Schema 2020-12，根类型必须为 object；使用 `jsonschema` 强制校验。
> - 只允许包内相对路径和内部 `$ref`；拒绝绝对路径、符号链接、目录穿越、网络引用、未知 manifest 字段及超限文件。
> - 用户级目录使用 XDG/macOS Application Support 下的 `capslock/skills`；工作区目录为 `capslock.skills/`。
> - 同名工作区 Skill 覆盖用户 Skill；无效的工作区覆盖会阻断加载，不静默回退。
> - `/skills disable <name>` 默认仅在当前工作区禁用，并优先于两级注册表；`enable` 清除该禁用状态。
>
> CLI 接口：
>
> ```text
> /skills list
> /skills show <name-or-run-id>
> /skills validate <name>
> /skills run <name> [key=value ...]
> /skills enable <name>
> /skills disable <name>
> ```
>
> `run` 使用 schema 对 `key=value` 做类型转换，缺失必填字段时交互补齐，拒绝未知或重复参数。模型必须返回原始 JSON 并通过输出 schema；解析或校验失败时本次运行直接失败，不自动重试。
>
> ## 实现阶段
>
> 1. **契约、加载器与兼容检查，3 天**
>    - 新增 `SkillManifest`、`SkillPackage`、`SkillRegistry` 和结构化校验错误。
>    - 完成双层发现、覆盖、禁用、SemVer、最低 CapsLock 版本和工具依赖校验。
>    - 为 schema、指令和包大小设置固定上限，加载过程保持离线且不执行包内代码。
>
> 2. **受限运行时与审计，4–5 天**
>    - 新增 `WorkspaceAgent.run_skill()`，将 Skill 指令作为低于系统安全指令的工作流上下文注入。
>    - 从现有 `ToolRegistry` 创建声明工具子集；每次调用再次检查 Skill 状态、包摘要和工具参数。
>    - 对命令模板和 MCP 使用限定声明，例如 `command:pytest`、`mcp:<server>:<tool>`；文件路径、Web、MCP 和审批继续由现有策略二次校验。
>    - `PermissionMode` 保持不变；Skill 的有效能力只能是 manifest、当前会话权限和系统策略的交集。
>    - 文件变更、命令和外部动作必须属于当前 Skill run，禁止复用其他 run 的动作 ID。
>
> 3. **持久化与 CLI，2–3 天**
>    - 工作区 SQLite 升至 schema v4，新增 `skill_runs` 和 `skill_settings`；迁移前备份，失败事务回滚。
>    - `skill_runs` 保存名称、版本、来源、manifest 摘要、声明能力、状态、时间和脱敏后的输入/输出摘要。
>    - 即使 Skill 被禁用或删除，`/skills show <run-id>` 仍可查看历史元数据，并可关联原有 run、tool call、action 和事件审计。
>    - 接入斜杠命令目录、补全、输入提示和结构化结果渲染；不向模型注册 `run_skill` 工具，因此不存在隐式触发入口。
>
> 4. **安全验证、文档与发布，3–4 天**
>    - 提供一个只读示例 Skill、一个需要受控动作的示例及恶意/损坏测试包。
>    - 更新 README、Agent Reference、示例配置、v1.5 开发文档、CHANGELOG、roadmap 和发布说明。
>    - 将唯一版本源更新为 `1.5.0`，CI 全部通过后创建 `v1.5.0` tag 和 GitHub Release。
>
> ## 测试与验收
>
> - 包校验：未知字段、非法版本、版本不兼容、缺失工具、无效 schema、路径穿越、符号链接、外部 `$ref` 和大小限制。
> - 注册表：用户/工作区发现、同名覆盖、无效覆盖阻断、当前工作区禁用与重新启用。
> - 运行：参数转换、交互补齐、输入拒绝、合法结构化输出、非 JSON 输出和 schema 不匹配。
> - 权限：未声明工具不可见；命令模板和 MCP 工具不能越权；三种权限模式仍按原规则审批。
> - 生命周期：运行期间包被修改、禁用或删除时立即中止；历史审计保持可读。
> - 迁移：schema v3→v4 备份、幂等启动、失败回滚和旧版本回滚说明。
> - 跨平台：Linux/macOS、Python 3.11/3.12 得到一致的发现、路径和校验结果。
> - 发布门槛：现有 91 项回归测试与新增测试全部通过，同时通过 Ruff、依赖检查、`pip-audit`、仓库卫生、构建、twine、wheel 安装和版本一致性校验。
>
> ## 假设与边界
>
> - v1.5.0 不支持远程市场、自动下载、自动升级、隐式触发、后台运行或任意脚本入口。
> - Skill 包采用目录结构，禁用默认限定当前工作区，输出执行强制结构化校验。
> - Skill 指令和包内容均视为不可信数据，不能覆盖系统指令、权限模式或现有安全策略。
> - 实施时保留当前工作区中与 v1.5.0 无关的未提交文档改动。

> skill是如何接入到agent的？用户应该怎么调用？

Skill 不是作为新工具自动暴露给模型，而是作为一次“受限的 Agent 运行”接入。

调用链如下：

1. 用户输入 `/skills run ...`
2. CLI 解析输入并补齐 schema 必填字段：[skills.py](./capslock/cli/skills.py:17)
3. `SkillRegistry` 合并用户级和工作区级 Skill，并检查禁用状态：[registry.py](./capslock/skills/registry.py:31)
4. 加载并校验 manifest、路径、版本、工具、schema 和 fixtures：[manifest.py](./capslock/skills/manifest.py:86)
5. `WorkspaceAgent.run_skill()` 创建独立 run，将 Skill 指令和输入加入上下文：[runtime.py](./capslock/runtime.py:156)
6. 根据 `required_tools` 裁剪模型可见工具，并在每次调用前重新检查 Skill：[runtime.py](./capslock/runtime.py:308)
7. 模型输出必须是符合输出 schema 的 JSON object；结果及工具、动作状态写入 schema v4 审计。

Skill 不会自动触发，也不存在供模型调用的 `run_skill` 工具。只有用户输入 `/skills run` 才会执行。

**用户调用方式**

先将 Skill 放入工作区注册表。例如使用仓库附带的示例：

```bash
mkdir -p capslock.skills
cp -R examples/skills/workspace-summary capslock.skills/
capslock
```

进入会话后：

```text
/skills list
/skills validate workspace-summary
/skills show workspace-summary
/skills run workspace-summary root=.
```

如果缺少必填字段，也可以直接运行：

```text
/skills run workspace-summary
```

CLI 会根据输入 schema 询问：

```text
root>
```

多个参数使用 `key=value`：

```text
/skills run release-check target=src limit=20
```

字符串包含空格时使用引号：

```text
/skills run release-check topic="release planning"
```

管理命令：

```text
/skills disable workspace-summary
/skills enable workspace-summary
/skills show <skill-run-id>
```

禁用只影响当前工作区。包被删除后，仍可通过历史 run ID 查看脱敏审计记录。

用户级 Skill 目录为：

- Linux：`$XDG_DATA_HOME/capslock/skills/`，默认 `~/.local/share/capslock/skills/`
- macOS：`~/Library/Application Support/capslock/skills/`

同名工作区 Skill 会覆盖用户级 Skill，但无效的工作区包不会静默回退到用户级版本。

## 外部 Skill 的安全限制

CapsLock 会拒绝以下包：

- `skill.toml` 包含未知字段或缺少必填字段。
- 目录名和 manifest 的 `name` 不一致。
- 最低 CapsLock 版本高于当前版本。
- 声明不存在的工具或缺少相应权限声明。
- 使用绝对路径、`..` 路径穿越或符号链接。
- JSON Schema 使用外部 `$ref`、`$dynamicRef` 等网络引用。
- schema、instructions 或 fixtures 超出大小限制。
- fixtures 与声明的成功/失败预期不一致。

即使校验通过，外部 Skill 也不能获得任意 Shell，不能自动运行，不能扩大当前权限模式，也不能绕过文件、命令、Web 或 MCP 的审批与审计。

- CapsLock：强契约、显式执行、安全优先。
- Claude Code：开放标准、渐进披露、功能最丰富。

先澄清一点：CapsLock 的 `TOML + instructions + JSON Schema` 并不是“三层安全沙箱”。

- TOML 是静态能力和兼容性契约。
- instructions 是行为提示，仍然可能被模型误解。
- JSON Schema 只校验数据结构，不校验事实正确性。
- 真正的安全边界来自运行时工具裁剪、`WorkspacePolicy`、权限模式和 `ActionCoordinator`。

## 设计比较

| 维度 | CapsLock v1.5 | Claude Code | Codex |
|---|---|---|---|
| 入口文件 | `skill.toml` + `instructions.md` | `SKILL.md` | `SKILL.md` |
| 元数据 | 严格 TOML，未知字段拒绝 | YAML frontmatter，字段丰富且多数可选 | YAML frontmatter，核心是 `name`、`description` |
| 输入输出 | 强制 JSON Schema | 自由文本和位置参数，无强制输出 schema | 自由文本，无标准输出 schema |
| 触发方式 | 仅 `/skills run` 显式调用 | 自动匹配或 `/skill-name` | 用户点名或根据描述匹配 |
| 工具控制 | manifest 声明工具，运行时裁剪和二次校验 | `allowed-tools`、权限规则、Skill 工具 | Skill 描述工作流，实际工具由当前 Agent 环境和审批控制 |
| 附加资源 | 当前仅 instructions、schema、fixtures | scripts、references、assets、templates、subagent | scripts、references、assets、UI metadata |
| 脚本执行 | 不允许任意脚本 | 支持，并可动态注入命令输出 | 支持运行 Skill 自带脚本，但仍受沙箱和审批控制 |
| 输出可组合性 | 高 | 低到中 | 低到中 |
| 跨生态兼容 | 低，需要转换 | 遵循 Agent Skills 标准并扩展 | 接近 Agent Skills 的 `SKILL.md` 结构 |
| 安全哲学 | fail closed | 灵活性优先，权限系统兜底 | Agent 沙箱、审批和技能指引分层 |

## CapsLock 方案的优点

1. **能力边界可以静态审查**

看到以下声明，就能预先知道 Skill 需要什么：

```toml
required_tools = ["read_file", "command:pytest"]
required_permissions = ["workspace.read", "command.execute"]
```

这比从长篇 Markdown 中推断权限可靠得多。

2. **输入输出可机器组合**

JSON Schema 能在调用模型前拒绝错误输入，在模型返回后拒绝不合规输出。这适合：

- 发布检查
- 结构化提取
- 报告生成
- 后续工作流组合
- 自动化回归测试

3. **兼容性明确**

`schema_version`、Skill SemVer 和 `min_capslock_version` 可以在加载时处理不兼容问题，而不是运行到一半才失败。

4. **默认拒绝更加稳定**

未知字段、目录穿越、符号链接、外部 `$ref`、缺失工具都会阻止加载。不同操作系统上的校验结果更容易保持一致。

5. **审计更完整**

Skill 名称、版本、包摘要、输入输出摘要、工具和动作都关联到同一个 run。包被删除后，仍能确认当时执行了什么版本。

## CapsLock 方案的缺点

1. **创作成本明显更高**

一个很简单的提示词工作流也要维护四个文件。相比单一 `SKILL.md`，入门门槛更高。

2. **不适合探索型任务**

研究、写作、设计讨论经常无法预先定义稳定输出 schema。强制 JSON 会让模型为了满足格式而牺牲自然表达。

3. **生态兼容性差**

Claude Code、Codex 和 Agent Skills 生态中的现有 Skill 基本都要转换，不能直接复制使用。

4. **存在重复声明**

工具已经能推导权限，但 manifest 仍要求同时写：

```toml
required_tools = ["read_file"]
required_permissions = ["workspace.read"]
```

这会产生配置漂移，需要加载器持续检查二者一致性。

5. **Schema 只保证形状**

下面的结果可能完全符合 schema，但内容仍然错误：

```json
{
  "ready": true,
  "summary": "所有检查都通过",
  "issues": []
}
```

因此仍然需要证据、引用、评测或确定性检查。

6. **扩展成本较高**

增加新的 manifest 字段、输出模式或资源类型，需要处理 schema 版本、旧包兼容和加载器升级。

## Claude Code 的设计

Claude Code 使用 `SKILL.md` 作为入口：

```yaml
---
name: deploy
description: Deploy the application
disable-model-invocation: true
allowed-tools: Bash(npm test *) Read
context: fork
agent: general-purpose
---

部署步骤……
```

主要特点：

- 只把名称和描述放入 Skill 列表，正文触发后才进入上下文。
- Claude 可根据 `description` 自动选择，也可以用 `/deploy` 显式调用。
- 支持 `$ARGUMENTS`、命名参数和 `${CLAUDE_SKILL_DIR}`。
- 支持 `scripts/`、`references/`、模板和 assets 按需加载。
- 支持动态命令注入，例如 ``!`git diff HEAD` ``。
- 支持 `context: fork` 在子 Agent 中运行。
- 项目、用户、企业、插件和嵌套目录都有独立发现规则。
- 可以通过 `disable-model-invocation`、`skillOverrides` 和权限规则控制可见性。

它的优势是低创作成本和极高表现力；缺点是输入输出契约弱、自动触发存在误触发/漏触发、脚本和动态命令扩大了攻击面。

官方资料：[Claude Code Skills](https://code.claude.com/docs/en/skills)。

## Codex 的设计

当前 Codex Skill 同样以 `SKILL.md` 为中心：

```text
skill-name/
├── SKILL.md
├── agents/openai.yaml
├── scripts/
├── references/
└── assets/
```

核心逻辑：

- YAML frontmatter 的 `name` 和 `description` 用于发现与触发。
- `SKILL.md` 正文只在 Skill 被选择后完整加载。
- Skill 可以要求继续读取特定 reference、运行自带脚本或使用 assets。
- `agents/openai.yaml` 提供列表展示、简短描述和默认 prompt 等 UI 信息。
- Skill 本身不授予权限；实际文件、命令、网络和外部工具仍由 Codex 当前沙箱、审批策略和工具可用性决定。
- 更复杂的分发单元是 Plugin，可以同时包含 Skills、命令、MCP、hooks 和 assets。
- 没有统一的运行时输入/输出 JSON Schema；输出质量主要依靠说明、脚本、测试和 Agent 验证。

本环境中的 Codex Skill authoring 规范见 [SKILL.md](/root/.codex/skills/.system/skill-creator/SKILL.md:56)。OpenAI 官方入口为 [Codex customization](https://developers.openai.com/codex/concepts/customization#skills)，但本环境抓取官方站点时收到 HTTP 403，因此这里也结合了当前安装环境实际执行的 Skill 规则。

## 对 CapsLock 的建议

不建议完全放弃当前强契约，但可以改成“分层严格度”：

- `structured` Skill：保留强制输入/输出 schema，适合自动化。
- `conversational` Skill：输入 schema 可选，允许 Markdown 文本输出。
- `reference` Skill：只提供知识和规则，不产生独立 run。
- 增加 `references/` 和 `assets/` 的按需加载，并全部纳入摘要。
- 提供 `SKILL.md` 导入转换器，生成 CapsLock TOML 和 schema，而不是直接信任外部包。
- 自动触发以后再做，并要求 manifest 显式声明 `invocation = "manual" | "suggest" | "automatic"`。
- scripts 暂时保持禁止；等插件隔离、签名和沙箱成熟后再开放。

这样可以保留 CapsLock 的安全优势，同时降低与 Claude Code、Codex Skill 生态之间的转换成本。

用户级目录继续采用 XDG/macOS 原生数据目录也比 `~/.capslock/skills` 更符合跨平台规范。

```text
├── skills/              # 可提交

└── state/               # 忽略

    ├── events.jsonl
    └── backups/
```

1. 将运行数据迁移到 `.capslock/state/`。
2. `.gitignore` 只忽略 `state/` 和 `local/`。

4. 路径策略只允许经过审批后修改 `.capslock/skills/`，继续禁止修改 state。
5. 提供旧 `capslock.skills/` 和旧数据库位置的兼容发现与迁移。
6. 两个位置同时存在时明确报冲突，避免静默覆盖。

> layout是干什么用的

`layout` 是 CapsLock 的统一路径管理层，负责回答“某类数据实际应该放在哪里、当前应该读取新路径还是旧路径”。

主要职责：

- 定义项目路径：
  - `.capslock/config.toml`
  - `.capslock/mcp.json`
  - `.capslock/skills/`
  - `.capslock/local/`
  - `.capslock/state/`

- 定义用户路径：
  - `${CAPSLOCK_HOME:-~/.capslock}/skills/`
  - `${CAPSLOCK_HOME:-~/.capslock}/state/memory.sqlite3`

- 兼容旧布局：旧路径单独存在时继续读取，并产生迁移警告。

- 检测冲突：例如新旧配置内容不同，或新旧数据库同时存在时拒绝启动，防止数据分叉。

- 提供迁移能力：`LayoutMigrator` 实现 dry-run、复制、摘要校验、原子落盘和旧文件清理。

以前各模块会自行拼接路径，例如：

```python
workspace / ".capslock" / "capslock.sqlite3"
```

现在统一通过：

```python
layout.database
layout.events
layout.skills
layout.user.memory
```

这样配置、CLI、sessions、MCP、Skill 和 memory 使用的是同一套目录规则。核心代码在 [layout.py](./capslock/layout.py:19)，CLI 在 [app.py](./capslock/cli/app.py:88) 启动时创建一次 `ProjectLayout`，然后传给其他组件。

CapsLock 的渐进式披露分为三层：目录信息、Skill 正文、具体资源。这里的“披露”指进入模型上下文的内容逐步增加，不代表 CapsLock 进程完全延迟读取文件。

```text
项目/用户 Skill 目录
        │
        ▼
解析并校验 SKILL.md
        │
        ▼
Catalog：名称 + 描述
        │
        ▼
模型判断是否相关
        │
        ├─ 不相关：不加载
        │
        └─ 相关：load_skill(name)
                     │
                     ▼
              正文 + 资源清单
                     │
                     └─ read_skill_resource(...)
                              │
                              ▼
                       指定资源的指定行
```

**1. 发现与校验**

启动 `WorkspaceAgent` 时创建 `SkillRegistry` 和单次运行缓存 `SkillService`，见 [runtime.py](./capslock/runtime.py:89)。

注册表只扫描：

- `.capslock/skills/`
- `${CAPSLOCK_HOME:-~/.capslock}/skills/`

用户级先加载，项目级同名覆盖用户级，见 [registry.py](./capslock/skills/registry.py:55)。

发现包时，CapsLock 会读取完整 `SKILL.md` 进行 frontmatter、正文、资源、符号链接和大小校验，见 [manifest.py](./capslock/skills/manifest.py:80)。因此磁盘读取不是完全延迟的，但正文此时不会发送给模型。

**2. 第一层：Catalog**

每次普通 run 构建系统指令时，注册表生成最多 16 KiB 的 catalog：

```text
- $my-summary: Summarize a workspace area...
- $another-skill
```

只包含有效、启用 Skill 的名称和描述，见 [registry.py](./capslock/skills/registry.py:73)。

超出预算后：

- 所有名称继续保留。
- 按名称顺序填充描述。
- 放不下的描述退化为 name-only。

Catalog 被放入 `<available-skills>` 系统上下文，并告诉模型只有匹配任务时才调用 `load_skill`，见 [runtime.py](./capslock/runtime.py:169)。

**3. 第二层：加载 Skill 正文**

模型判断某个 Skill 与用户请求匹配后，产生工具调用：

```json
{"name": "load_skill", "arguments": {"name": "my-summary"}}
```

`ToolLoop` 执行工具并把结果作为 `tool` 消息追加到上下文，随后再次调用模型，见 [runtime_support.py](./capslock/runtime_support.py:83)。

`load_skill` 返回：

```json
{
  "name": "my-summary",
  "description": "...",
  "scope": "workspace",
  "digest": "...",
  "instructions": "完整 Markdown 正文",
  "resources": [
    {"path": "references/guide.md", "size": 1200, "kind": "references"}
  ]
}
```

实现位于 [skills.py](./capslock/tooling/skills.py:10) 和 [service.py](./capslock/skills/service.py:54)。

加载时会：

- 校验 Skill 仍然有效且启用。
- 将所有资源读取为当前 run 的内存快照。
- 按 `(run_id, skill_name)` 缓存。
- 记录 `skill_loaded` 事件。
- 重复加载直接返回相同快照。

审计记录只保存名称、scope、digest、触发方式和资源数量，不保存正文。

**4. 第三层：读取具体资源**

模型看到资源清单后，只有确实需要某个文件时才调用：

```json
{
  "name": "read_skill_resource",
  "arguments": {
    "name": "my-summary",
    "path": "references/guide.md",
    "start_line": 1,
    "end_line": 40
  }
}
```

读取必须满足：

- Skill 已在当前 run 加载。
- 路径属于包内资源。
- 使用内存快照，不重新读磁盘。
- 内容小于 512 KiB。
- 内容为 UTF-8。
- 行范围合法。
- 拒绝路径穿越、二进制和符号链接。

实现见 [service.py](./capslock/skills/service.py:78)。

`scripts/` 与其他资源一样只能列出或作为 UTF-8 文本读取，没有脚本执行工具。

**5. 显式 `$skill-name` 链路**

显式调用会跳过“模型根据 catalog 选择”的步骤：

```text
$my-summary focus on release readiness
```

处理链路：

```text
解析 $my-summary
  → registry.get("my-summary")
  → SkillService.load(trigger="explicit")
  → 建立资源快照
  → 正文和原始参数编码为不可信 JSON 上下文
  → 进入普通 ToolLoop
  → 返回普通文本答案
```

对应实现见 [runtime.py](./capslock/runtime.py:127) 和 [runtime.py](./capslock/runtime.py:183)。

未知、禁用或无效 Skill 会在调用模型前失败。

**6. 权限与清理**

Skill 加载不会授予权限。后续文件、命令、Web、MCP 和 memory 工具仍使用当前普通 `RunContext`、`WorkspacePolicy` 和 `PermissionMode`，见 [runtime.py](./capslock/runtime.py:208)。

run 无论成功、失败或取消，最终都会清除该 run 的 Skill 快照，见 [runtime.py](./capslock/runtime.py:166) 和 [service.py](./capslock/skills/service.py:129)。

因此模型上下文中的披露顺序是：

```text
名称/描述 → 完整正文/资源清单 → 单个资源片段
```

而不是启动时把所有 Skill 正文和资源一次性塞给模型。

```text
调用时才把全文披露给模型
```

CapsLock 当前也类似。注册表发现 Skill 时已经解析正文并计算整个包的摘要，参见 [`manifest.py`](<./capslock/skills/manifest.py:80>)。

2. 初始上下文只披露名称和描述

Claude Code 将 Skill 编排为：

```text
- pdf: Process PDF documents...
- commit: Create a Git commit...
```

这个 catalog 使用上下文窗口的 1%，默认约 8,000 字符，并限制单个描述最多 250 字符，见 [`prompt.ts`](<~/workspace/claude-code-src/src/tools/SkillTool/prompt.ts:20>)。

预算不足时：

- 优先压缩描述
- 极端情况下只保留 Skill 名称
- bundled Skill 的完整描述优先保留

最终 catalog 作为 `skill_listing` attachment 发给模型，并且同一 agent 通常只发送一次，见 [`attachments.ts`](<~/workspace/claude-code-src/src/utils/attachments.ts:2661>)。

CapsLock 对应的是固定 16 KiB catalog，见 [`registry.py`](<./capslock/skills/registry.py:14>)。

3. 模型通过 `Skill` 工具加载正文

Claude Code 给模型提供的是统一的 `Skill` 工具：

```json
{
  "skill": "pdf",
  "args": "document.pdf"
}
```

工具会检查 Skill 是否存在、是否允许模型调用，然后进入 `processPromptSlashCommand`，见 [`SkillTool.ts`](<~/workspace/claude-code-src/src/tools/SkillTool/SkillTool.ts:634>)。

调用时，之前保存在闭包里的 Markdown 正文才被构造成模型消息：

```text
Base directory for this skill: /path/to/skill

<完整 SKILL.md 正文>
```

对应代码在 [`loadSkillsDir.ts`](<~/workspace/claude-code-src/src/skills/loadSkillsDir.ts:344>)。随后作为 `isMeta: true` 的用户消息注入当前会话，见 [`processSlashCommand.tsx`](<~/workspace/claude-code-src/src/utils/processUserInput/processSlashCommand.tsx:869>)。

CapsLock 将这个步骤拆成了显式的只读工具 `load_skill(name)`，见 [`skills.py`](<./capslock/tooling/skills.py:10>)。

4. Claude Code 没有专门的 `read_skill_resource`

这是两者最明显的区别。

Claude Code 把 Skill 根目录写进正文，然后让模型使用普通文件工具读取：

```text
SKILL.md 提到 references/api.md
    ↓
模型调用普通 Read/Grep
    ↓
读取 Skill 目录里的文件
```

也就是说，资源的第二级披露依赖通用 `Read/Grep/Bash`，不是专用 Skill API。

CapsLock 则使用：

```text
load_skill(name)
    ↓
返回正文和资源清单
    ↓
read_skill_resource(name, path, start_line, end_line)
```

并对 UTF-8、文件大小、路径穿越和行范围做统一校验，见 [`service.py`](<./capslock/skills/service.py:78>)。

5. Claude Code 的 Skill 可以携带行为配置

本地源码显示 Claude Code 支持：

- `allowed-tools`
- `disable-model-invocation`
- `user-invocable`
- `hooks`
- `context: fork`
- `agent`
- `model`
- `effort`

解析入口在 [`loadSkillsDir.ts`](<~/workspace/claude-code-src/src/skills/loadSkillsDir.ts:237>)。

其中 `allowed-tools` 会修改当前 Skill 调用的工具权限上下文；非 MCP Skill 还支持 Markdown 内嵌 shell 展开，见 [`loadSkillsDir.ts`](<~/workspace/claude-code-src/src/skills/loadSkillsDir.ts:356>)。

CapsLock 有意拒绝这些字段。Skill 只能提供工作流说明，不能授予权限、注册 hook、指定模型或获得脚本执行特权。这是安全策略差异，不是渐进式披露能力缺失。

6. Claude Code 会在压缩后保留已调用 Skill

Skill 被调用后，Claude Code 保存最终注入的正文，见 [`state.ts`](<~/workspace/claude-code-src/src/bootstrap/state.ts:1501>)。上下文压缩时不会重新发送完整 catalog，但会恢复已经调用过的 Skill 内容，见 [`postCompactCleanup.ts`](<~/workspace/claude-code-src/src/services/compact/postCompactCleanup.ts:17>)。

**结论**

CapsLock 当前实现与 Claude Code 的核心模型一致：

```text
名称/描述发现 → 选择 Skill → 披露正文 → 按需读取资源
```

但 CapsLock 更严格、更结构化：

| 环节 | Claude Code | CapsLock |
|---|---|---|
| 初始 catalog | 1% 上下文，默认 8 KiB | 固定 16 KiB |
| 正文加载 | `Skill` 工具注入消息 | `load_skill` 返回结构化结果 |
| 资源读取 | 普通 Read/Grep/Bash | `read_skill_resource` |
| 运行快照 | 保存已调用正文用于压缩恢复 | 每个 run 快照整个资源包 |
| 行为字段 | 支持权限、hook、fork、model 等 | 明确拒绝 |
| 显式调用 | `/skill args` | `$skill args` |
| 脚本 | 可以通过普通 Bash 执行 | 无 Skill 专属执行能力 |

所以答案是：整体链路确实是同一种渐进式披露思想；CapsLock 并非照搬 Claude Code，而是采用了更强隔离、更容易审计的变体。
