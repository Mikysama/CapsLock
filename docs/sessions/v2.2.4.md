## 结论

CapsLock 当前架构基础其实比 Claude Code 更规整：组合根、领域模型、repository、事务状态机、统一审批链和子 Agent 隔离都做得不错。真正需要优化的不是继续增加目录或抽象层，而是让现有边界“真正生效”。

优先级最高的四项是：

1. 插件从“权限声明”升级为真实的进程级隔离。
2. 上下文管理从“消息条数截断”升级为 token 感知的压缩体系。
3. 把运行编排真正从 `WorkspaceAgent` 中抽离。
4. 为工具补充能力元数据，并安全地并行只读工具。

本地 Claude Code 是约 51 万行的非官方源码快照，CapsLock 约 2.5 万行，因此这里比较的是机制，不是功能数量。

## 架构对比

| 维度 | CapsLock | Claude Code | 判断 |
|---|---|---|---|
| 核心边界 | domain / ports / application / runtime / storage 分层清楚 | 更偏产品模块化，存在大型上下文对象与中心引擎 | CapsLock 更干净 |
| 运行状态 | SQLite 事务、明确状态机、唯一终止事件 | 会话内存状态、transcript、SDK event 并存 | CapsLock 的可恢复性更强 |
| 工具模型 | schema + executor，统一进入 ActionCoordinator | 类型化输入/输出、并发性、只读性、中断、权限、进度、结果限制 | Claude Code 更成熟 |

| 权限安全 | 固定命令模板、动作先审批后执行 | 规则、hook、classifier、sandbox 多层组合 | CapsLock 更简单可靠，但插件隔离有缺口 |

## 优化建议

### P0：让插件权限成为真实安全边界

CapsLock manifest 声明了文件、网络、进程、凭据等权限，[manifest.py](./capslock/plugins/manifest.py:29) 也会验证 workspace grant；但执行时只是以缩减后的环境变量直接启动普通子进程，[client.py](./capslock/plugins/client.py:56)。插件仍可以通过 Python/系统调用读取用户目录、访问网络或启动其他进程。

因此目前的权限更接近“授权与审计声明”，不是强制隔离。

建议：

- 引入 `PluginSandbox` port，把进程启动从 `PluginProcessClient` 中移出。
- Linux 使用 namespace/seccomp/landlock 或成熟 sandbox runtime；macOS 使用 sandbox profile。
- 文件、网络、凭据尽量改成 capability broker，由 CapsLock 代理访问，而不是直接暴露给插件进程。
- 无法提供强隔离的平台应明确标成 `trusted-native-plugin`，不要显示成细粒度权限已生效。
- 隔离完成后再考虑常驻插件进程池、健康检查和崩溃重启。

Claude Code 至少将 shell sandbox 抽成了独立适配层，[sandbox-adapter.ts](~/workspace/claude-code-src/src/utils/sandbox/sandbox-adapter.ts:1)。

### P1：建立 token 感知的上下文管理器

CapsLock 当前在消息数超过阈值时压缩，[context.py](./capslock/runtime/context.py:26)；所谓摘要实际上是旧消息拼接后保留最后 6000 个字符，[sessions.py](./capslock/storage/repositories/sessions.py:209)。

主要问题：

- 长代码、工具输出和短对话成本差异巨大，消息数不能代表上下文大小。
- 字符截断可能丢失任务目标、决策和文件修改信息。
- 配置中已有 `context_window`，但没有参与 context 构建。
- checkpoint 保存完整 messages，长 run 恢复时仍可能越界。

建议新增 `ContextBudgetManager`：

- 预算使用 `profile.context_window - max_output_tokens - safety_margin`。
- 分层处理：先外置大型工具结果，再清理陈旧结果，最后做语义摘要。
- 摘要作为带版本、覆盖消息边界和 token 统计的持久化 artifact，而不是覆盖单个 session 字段。
- 保存关键事实、用户约束、未完成任务、文件变更和审批状态，原 transcript 保持可追溯。
- 连续压缩失败达到阈值后熔断，避免重复调用模型。

Claude Code 的 token 阈值、缓冲区和失败熔断可作为设计参考，[autoCompact.ts](~/workspace/claude-code-src/src/services/compact/autoCompact.ts:28)，但不用复制它整套复杂实现。

### P1：完成 `WorkspaceAgent` 的职责拆分

[agent.py](./capslock/runtime/agent.py:77) 同时持有模型、repository、workflow、memory、Skill、工具、审批、引用和协作；实际运行主流程也仍在 Agent 内部，[agent.py](./capslock/runtime/agent.py:241)。

与此同时，[execution.py](./capslock/runtime/execution.py:11) 只是回调 `agent._run_execution()`，没有真正拥有执行逻辑；`WorkspaceServicesPort` 甚至仍标注为 legacy，[services.py](./capslock/ports/services.py:1)。

建议目标：

```text
WorkspaceAgent（公开 facade）
    -> RunEngine
       -> ContextService
       -> ToolLoop
       -> RunFinalizer
       -> MemoryPostProcessor
```

同时：

- 删除 `WorkspaceServicesPort` 聚合口，按用例注入窄 port。
- 将 `Any` 类型的 memory、collaboration、prepared run、checkpoint 替换成稳定 DTO/Protocol。
- `ForegroundRunController` 只依赖 `AgentPort`，不要访问 `agent.repositories`。
- 组合根可拆成 storage、runtime、extension 三个 builder，`WorkspaceApplication.open()` 只负责资源所有权。

Claude Code 的 `QueryEngine` 虽实现了独立会话引擎，但其配置对象也已非常庞大，[QueryEngine.ts](~/workspace/claude-code-src/src/QueryEngine.ts:130)；这一点不应照搬。

### P1：扩展工具契约并安全并发

CapsLock 的 `Tool` 目前只有名称、描述、JSON Schema 和 executor，[async_core.py](./capslock/tooling/async_core.py:65)，同一模型返回的多个 tool call 会逐个执行，[tool_loop.py](./capslock/runtime/tool_loop.py:413)。

建议增加：

```python
ToolCapabilities(
    read_only=True,
    concurrency_safe=True,
    destructive=False,
    interrupt_behavior="cancel",
    max_result_bytes=...,
    external_side_effect=False,
)
```

调度器按连续批次执行：

- `concurrency_safe=True` 的只读工具限流并发。
- 写工具、审批工具和带 context mutation 的工具严格串行。
- 默认全部视为不安全，必须显式声明。
- 每个调用使用独立结果缓冲，最后按原 tool-call 顺序写入 messages/checkpoint。
- 如果引入并发读取，SQLite 需要独立只读连接或连接池，不能所有操作继续争用一个全局 connection lock。

Claude Code 对应实现见 [toolOrchestration.ts](~/workspace/claude-code-src/src/services/tools/toolOrchestration.ts:19) 和工具能力契约 [Tool.ts](~/workspace/claude-code-src/src/Tool.ts:362)。

当前 CapsLock 只有 20 个工具、schema 约 6.8 KiB，因此 Claude Code 的 deferred tool discovery 暂时不是重点。

### P2：异步化事件与可观测性

[observability.py](./capslock/observability.py:19) 会在事件循环中同步打开、追加、关闭 JSONL 文件，同时把所有事件永久保存在内存列表。流式 `text_delta` 较多时会增加延迟并导致长会话内存增长。

建议：

- 使用单写者异步队列和批量 flush。
- 内存只保留有界 ring buffer。
- 明确 critical event 与 best-effort telemetry；终止事件不可丢，进度事件允许合并。
- 增加 run/model/tool/action 的 correlation ID、延迟分位数和错误分类。
- JSONL、SQLite event 和未来 trace 共用一个结构化事件 envelope，避免三套字段逐渐漂移。

### P2：启动路径与按需装配

本机测得 `import capslock.cli.app` 约 `1.74s / 80MB`，只能作为当前环境基线，但说明静态导入值得关注。组合根还会串行打开两套数据库并加载 Skill/plugin 配置，[bootstrap.py](./capslock/bootstrap.py:86)。

建议：

- CLI 子命令采用延迟导入，`doctor`、`plugin`、`sessions` 不加载 TUI 和完整 runtime。
- workspace DB 与 memory DB 并行打开。
- fullscreen、FastEmbed、MCP、协作和插件运行时按能力首次使用时加载。
- 增加 `StartupProfiler`，分别记录 import、config、DB、credential、plugin scan 和 first render。
- 优化目标应是首屏/首提示符时间，而不只是进程总启动时间。

### P3：只增加“内部生命周期管线”，不要直接复制任意 Hook

Claude Code 在工具前后、权限、会话和压缩阶段都有 hook，工具执行链也统一执行 schema 校验、权限与 hook，[toolExecution.ts](~/workspace/claude-code-src/src/services/tools/toolExecution.ts:614)。扩展性很强，但安全与调试复杂度也很高。

CapsLock 更合适的做法是先引入内部、类型化 middleware：

```text
validate -> assess risk -> authorize -> execute -> sanitize -> persist -> publish
```

仅允许可信内置组件参与阻断或修改参数；第三方插件先只接收脱敏后的观察事件。这样能统一审计、指标和展示逻辑，又不会让 hook 成为新的授权旁路。

## 推荐实施顺序

1. 插件 sandbox/capability broker。
2. `ContextBudgetManager` 和版本化压缩 artifact。
3. 将 `_run_execution()` 移入真正独立的 `RunEngine`，收紧 ports。
4. `ToolCapabilities`、只读并发调度和结果外置。
5. 异步事件管线、启动 profiler 与延迟加载。
6. 最后再考虑内部 middleware、动态工具发现和更广的插件能力。

> # CapsLock 3.0 架构优化实施计划
>
> ## Summary
>
> 将 CapsLock 3.0 定位为一次安全边界与运行内核升级，分阶段完成：
>
> 1. 重构 RunEngine、ports 和工具执行契约。
> 2. 引入 token 感知上下文压缩与工具结果外置。
> 3. 发布 Plugin SDK v3、OS sandbox 与 capability broker。
> 4. 重构事件、存储并发和启动路径。
> 5. 统一迁移至 config、JSONL、archive、plugin protocol v3。
>
> 保持产品定位不变：本机前台运行、固定命令模板、单层子 Agent；不增加任意 Shell、远程控制、后台 daemon 或第三方可执行 Hook。
>
> ## Key Changes
>
> ### 1. 运行内核与公开接口
>
> - 新增 `AgentSession.run_stream(RunRequest)` 作为唯一运行入口；`WorkspaceApplication` 暴露 `session` 和只读 `queries`，删除 CLI 对 repository 的直接访问。
> - 删除 `WorkspaceAgent` 的聚合构造接口、`RunExecutionService` 和 legacy `WorkspaceServicesPort`；由 `RunEngine` 独立拥有准备、上下文、工具循环、收尾和取消逻辑。
> - 每个 session 使用串行执行锁；模型切换、恢复和新 run 不得与活动 run 交叉。
> - 所有 port 使用明确 DTO，移除核心路径中的 `Any`、任意 `**values` 和 repository bundle。
> - 内部执行固定为：`validate → middleware → authorize → execute → sanitize → persist → publish`。Middleware 仅供内置策略、审计和指标使用，第三方只能订阅脱敏事件。
>
> ### 2. 工具契约、并发与结果存储
>
> - 新增 `ToolSpec`、`ToolCapabilities`、`ExecutionContext`：
>   - 输入/输出 JSON Schema；
>   - `read_only`、`concurrency_safe`、`destructive`；
>   - `interrupt_behavior`；
>   - inline/result 大小上限；
>   - 外部副作用和所需 capability。
> - 通过统一 JSON Schema validator 校验模型及插件参数；语义校验作为工具自身的第二阶段。
> - 连续的 `concurrency_safe` 只读工具使用有界 `TaskGroup` 并发，默认上限 4；写入、审批、context mutation 工具独占执行。结果按原 tool-call 顺序写入 checkpoint。
> - 超过 16 KiB 的工具结果写入 `.capslock/state/artifacts/sha256/`，采用原子写入、0600 权限、SHA-256 校验和单项 5 MiB 硬上限；模型只接收脱敏预览与 artifact ID。
> - 新增只读、分块的 `read_tool_artifact`，仅允许当前 session 访问自己的 artifact。session 删除时级联清理。
> - SQLite 调整为单 writer 加小型只读连接池；复合状态转换继续由 writer transaction/UoW 独占。
>
> ### 3. Token 感知上下文
>
