<details><summary>4 previous messages</summary>

> 我会先梳理仓库结构、依赖关系和核心调用链，再按“耦合症状、可拆边界、重构收益与风险”给出具体候选模块。此轮只做检查和分析，不修改代码。
>
> 初步看，仓库已经具备 domain／ports／repository 的分层骨架；真正值得关注的不是“有没有分层”，而是组合根、运行时循环、CLI/TUI 与存储门面是否仍承担了过多职责。我正在用文件规模、入/出依赖和跨层导入来验证这些热点。
>
> 目前已有两个很明确的高优先级边界：`bootstrap.py` 把主应用装配与子 Agent 运行协议揉在一个 466 行的 `open()` 中；`configuration/service.py` 虽然新增了 pipeline/document 文件，但验证、迁移、环境解析和所有配置模型仍集中在 828 行服务文件里。下一步我会核对其余候选是否只是“文件大”，还是确实存在职责与依赖耦合。
>
> 现有测试基线是健康的：工作区虚拟环境下 `209 passed`。因此这些建议适合按“小步提取＋保持现有接口的兼容门面”推进，不需要大爆炸式重写；重点会放在降低未来修改的影响面，而不是修复当前功能错误。
</details>

结论：CapsLock 已有 `domain / ports / application / storage / runtime` 的分层基础，但仍有 8 个明显的解耦热点。优先处理组合根、生命周期、配置和存储聚合，收益最大。

## 高优先级

| 模块 | 耦合证据 | 建议拆分边界 |
|---|---|---|
| [bootstrap.py](./capslock/bootstrap.py:78) | 629 行；`WorkspaceApplication.open()` 达 466 行，内部 `child_runner()` 270 行。混合资源管理、模型路由、工具、动作、插件、记忆、子 Agent 权限和输出解析 | 提取 `ApplicationAssembler`、`ActionFactory`、`ModelFactory`、独立 `ChildAgentRunner`；组合根只负责装配和资源释放 |
| [lifecycle/service.py](./capslock/lifecycle/service.py:54) | 861 行，同时负责备份、恢复、导入导出、锁、journal、SQLite 合并和兼容格式；与 [coordinator.py](./capslock/lifecycle/coordinator.py:24) 存在双向导入 | 拆为 `BackupService`、`PortableArchiveService`、`ImportMergeEngine`、`LifecycleTransaction/LockManager`；消除 coordinator 对 service 私有函数的反向依赖 |
| [configuration/service.py](./capslock/configuration/service.py:30) | 828 行，配置模型、环境解析、验证、迁移、凭据解析和模型路由配置集中在一起；现有 `pipeline.py` 基本只是回调包装 | 拆成 `types.py`、`resolver.py`、`validation.py`、`migration.py`、`model_routes.py`；纯验证不得解析真实凭据 |
| [memory_repositories/lifecycle.py](./capslock/storage/memory_repositories/lifecycle.py:31) | `MemoryRepository` 504 行，实际包含生命周期、查询、来源、设置、访问记录和审计；[facades.py](./capslock/storage/memory_repositories/facades.py:10) 只是把调用转发回同一对象 | 把代码真正移动到 `MemoryLifecycleRepository`、`MemoryQueryRepository`、`MemorySourceRepository`、`MemorySettingsRepository`、`MemoryAuditRepository`；旧 `memories` 属性可暂时作为兼容门面 |

## 中高优先级

- [storage/repositories/workflow.py](./capslock/storage/repositories/workflow.py:28)：648 行，同时管理队列、run、step、event、工具审计、引用、审批结算和费用。建议拆成 `WorkItemRepository`、`RunJournalRepository`、`RunUsageQuery`，跨表的 `start/finalize/settle_approval` 保留在事务型 `WorkflowUnitOfWork` 中，避免为了拆文件破坏原子性。

- [runtime/agent.py](./capslock/runtime/agent.py:233)：`_execute()` 311 行，承担 Skill 加载、上下文构造、工具循环、引用解析、记忆提取、审批探测、终止 payload 构造和异常状态转换。建议提取 `RunExecutionService`、`RunOutcomeBuilder`、`PostRunMemoryCapture`，让 `WorkspaceAgent` 只保留公开流式接口和会话状态。

- [ports.py](./capslock/ports.py:266)：`WorkspaceServicesPort` 是较宽的 service locator，多个接口大量返回 `Any`。可以按 workflow、actions、memory、collaboration 拆分端口，并让 runtime 构造函数只接收它实际需要的窄接口。

- [action_system/core.py](./capslock/application/action_system/core.py:46)：直接依赖具体 `WorkspaceRepositories`；[external.py](./capslock/application/action_system/external.py:28) 也只为写 source 而接收整个 repository 聚合。同时 `core.py ↔ commands.py` 存在导入环。建议引入 `ActionRepositoryPort`、`RunStatePort`、`SourcePort`，并把重新校验逻辑下放到 handler，消除 coordinator 对命令模板的反向引用。

## 次优先级

- Inline 与 fullscreen TUI：
  [cli/tui.py](./capslock/cli/tui.py:51) 和 [fullscreen_tui/app.py](./capslock/cli/fullscreen_tui/app.py:387) 重复实现请求队列、worker、authorizer 安装、retry/start 和空会话清理。建议共享无 UI 依赖的 `ConversationController`，两个前端只保留渲染和交互。当前 CLI 相关模块形成了 7 模块导入强连通分量，也值得顺手解除。

- [runtime/routing.py](./capslock/runtime/routing.py:121)：631 行，`complete()` 与 `stream_complete()` 分别重复候选遍历、预算检查、重试和审计。可提取 `RoutePlanner`、`BudgetGate`、`AttemptExecutor`，统一非流式和流式调用的状态机。

- [cli/diagnostics.py](./capslock/cli/diagnostics.py:167)：`doctor()` 184 行、分支较多，同时检查和修复配置、数据库、MCP、Skill、插件及网络。适合改成可注册的 `DiagnosticProbe` 和 `DiagnosticFix`。

## 不建议仅因文件大而拆

- [storage/schema.py](./capslock/storage/schema.py)：主要是声明式 DDL，职责集中。
- [tooling/async_catalog.py](./capslock/tooling/async_catalog.py)：虽然注册函数较长，但本质是工具目录声明。
- [memory/service.py](./capslock/memory/service.py:53)：已经是对 recall、candidate、embedding、transfer 等聚焦服务的合理门面；应优先拆其底层 repository，而不是再拆门面。

推荐实施顺序：配置与 Memory Repository → 消除 lifecycle/action 导入环 → 提取 child runner → 拆 workflow/runtime → 共享 TUI controller → 最后整理 model routing。

检查基于当前未提交工作树；没有修改文件。测试基线为 `.venv/bin/pytest -q`：`209 passed`。

> ## 阶段四：组合根、运行时与模型路由
>
> - `WorkspaceApplication.open()` 只负责确定 workspace、建立资源生命周期并调用装配组件；使用统一异步资源栈保证任意中途失败只关闭一次。
> - 提取模型路由、动作 handler、Skill/Plugin、Memory 和 Agent 的构建器；组合根仍是唯一允许同时依赖具体 storage、runtime 和 application 的位置。
