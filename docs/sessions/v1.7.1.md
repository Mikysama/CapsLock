整体判断：代码库当前行为稳定，`165` 项测试、Ruff、仓库卫生检查全部通过。主要问题不是已有故障，而是 v1.6/v1.7 功能持续叠加后，工作流、存储、记忆和 CLI 边界开始重新变得模糊。

**最高优先级**

1. 收回 `SessionStore` 的数据库边界

[session.py](./capslock/session.py:13) 通过多继承聚合 8 个 repository，最终变成覆盖全部业务的“万能接口”。更严重的是上层开始直接访问 `_connection`：

- [runtime.py](./capslock/runtime.py:198) 查询可恢复 run。
- [cli/actions.py](./capslock/cli/actions.py:347) 完成等待审批的工作流。
- [cli/tui.py](./capslock/cli/tui.py:365) 查询可重试 run。
- [session_management.py](./capslock/session_management.py:61) 检查活跃任务，并从 [第 94 行](./capslock/session_management.py:94) 开始直接拼装整个导出数据集。

这使 schema 细节泄漏到 runtime、CLI 和会话管理层。审批完成还需要依次更新 action、run、work item 和 event，目前不是一个明确的原子业务操作，中途失败可能留下状态不一致。

建议：

- 在 `RunRepository`/`WorkflowRepository` 增加 `get_retryable_run()`、`settle_waiting_run()`、`has_active_work()`。
- 增加只读的 `SessionExportRepository` 或 `SessionSnapshotQuery`。
- 用组合代替 `SessionStore` 的 repository 多继承；短期可保留 `SessionStore` facade 兼容现有调用。
- 将 `settle_workflow()` 从 CLI 移入应用层，并在单个事务中完成状态转换。

2. 缩小 `WorkspaceAgent`，让组合根真正负责装配

[WorkspaceApplication](./capslock/application/app.py:28) 把 20 多个配置原语传给 [WorkspaceAgent](./capslock/runtime.py:70)，Agent 又自行创建 Skill、Memory、ToolLoop、ContextBuilder 和 ActionCoordinator。

同一套 ActionCoordinator 配置至少装配了三次：

- [WorkspaceAgent._run_context()](./capslock/runtime.py:396)
- [cli/actions.py](./capslock/cli/actions.py:42)
- Agent 初始化时保存的各个 timeout/limit 字段

而 [_ask_async()](./capslock/runtime.py:181) 同时承担队列、恢复、Skill、上下文、模型循环、记忆提取、消息持久化、run 状态和异常补偿。

建议拆成：

- `WorkspaceAgent`：稳定的 `ask/enqueue/ask_stream` facade。
- `WorkflowRunner`：执行一次请求。
- `RunLifecycleService`：run/work-item/event 状态机。
- `RunContextFactory`：统一构造 ActionCoordinator 和工具上下文。
- `WorkspaceApplication`：唯一组合根，直接注入这些依赖和完整的配置对象。

**高收益重构**

3. 按业务能力拆分记忆模块

[memory.py](./capslock/memory.py:58) 有 1077 行，`MemoryService` 同时负责：

- CRUD、权限和设置。
- FTS/向量混合召回与评分。
- 模型候选提取和冲突协调。
- 候选审核与自动采纳。
- JSON 导入导出和文件安全。
- 向量索引维护。

[storage/memory.py](./capslock/storage/memory.py:113) 也有 1143 行，混合了 schema 迁移、记忆 CRUD、候选、来源、设置、embedding、recall 和 audit。

建议保留 `MemoryService`/`MemoryStore` 兼容 facade，内部拆为：

- `memory/service.py`：手动生命周期和权限。
- `memory/recall.py`：排名、阈值、上下文构造。
- `memory/candidates.py`：提取、协调、审核、自动采纳。
- `memory/transfer.py`：版本化导入导出。
- `storage/memory_migrations.py`
- `storage/memory_repository.py`、`candidate_repository.py`、`embedding_repository.py`

不要合并工作区数据库和用户记忆数据库，两者的生命周期与作用域隔离是合理的产品边界。

4. 删除 ToolLoop 的同步/异步双实现

[ToolLoop.run()](./capslock/runtime_support.py:109) 与 [run_async()](./capslock/runtime_support.py:149) 重复了工具参数解析、证据归集、审计和消息追加。

仓库中只有 [run_async 的生产调用](./capslock/runtime.py:262)，同步版本目前没有调用者，而且同步版缺少流事件、checkpoint 和异步 MCP 自动执行逻辑。

建议以异步循环为唯一实现；如需兼容同步 API，让同步入口只负责 `asyncio.run()` 和空事件回调。这样可以避免两条执行语义继续漂移。

5. 将动作类型分派改为 handler 边界

[ActionCoordinator](./capslock/application/actions.py:66) 在 propose、approve、execute、reject、record 五处重复按 `ActionType` 分支；`ChangeService`、`CommandService`、`ExternalActionService` 又各自实现相似的 pending/approved/running/completed 状态检查。

可以引入内部 `ActionHandler` 协议和类型注册表，Coordinator 只负责：

- session/run 所有权。
- 风险评估和审批策略。
- handler 选择。
- 统一状态机和审计。

文件、命令、Web、MCP handler 继续负责各自的安全校验和执行细节。

**次优先级**

6. 让 CLI 展示层变成纯展示层

[cli/render.py](./capslock/cli/render.py:128) 有 702 行，大量参数使用 `object`/`hasattr`，部分 render 函数还直接查询 Agent 和 Store，例如 [render_session_history()](./capslock/cli/render.py:172) 和 [render_workflow_status()](./capslock/cli/render.py:200)。

建议按 `workflow_views.py`、`memory_views.py`、`action_views.py`、`session_views.py` 拆分，并让 controller 先生成明确的 view model，render 函数只接收数据。

7. 抽出 Classic CLI 与 TUI 共用控制器

[tui.py](./capslock/cli/tui.py:37) 使用无类型的 `dict` 保存状态、三元 tuple 表示队列，还从 `chat.py` 导入私有 `_delete_empty_session` 和常量 [第 16 行](./capslock/cli/tui.py:16)。

建议增加 `InteractiveSessionController`、`TuiState`、`QueuedRequest`，统一请求确认、空会话清理、Web 续答和审批后续流程。Classic/TUI 只保留不同的输入输出策略。

8. 分离布局发现与迁移

[layout.py](./capslock/layout.py:19) 前半是运行时高频使用的目录契约，后半从 [LayoutMigrator](./capslock/layout.py:204) 开始是低频、带复制删除副作用的迁移实现。

可拆成 `layout.py` 和 `layout_migration.py`，减少常规启动路径对迁移实现的依赖。

**暂时不建议动**

`policy.py`、`security.py`、`evidence.py` 职责集中；`skills/` 已按 manifest/registry/service 分层；`tooling/` 的 core/catalog/adapter 拆分也比较健康。`tools.py` 只是兼容出口，适合保留到 v2 再删除。

推荐实施顺序是：先增加 repository/application API 并消除 `_connection` 访问，再迁移工作流状态机，随后拆 Memory，最后整理 CLI 和布局模块。每一步都保留现有 facade，可避免一次性目录重排造成大范围回归。

> # CapsLock v2 全量重构优化计划
>
> ## 总结
>
> 将 CapsLock 重构为异步、强边界的 v2 内核：重新设计两套 SQLite schema，消除上层直接 SQL，拆分运行时和记忆模块，统一动作状态机，并将 CLI 收敛为 TUI 与 JSONL exec 两种主要交互面。
>
> 采用多 PR 渐进交付。过渡期允许新旧实现并存，但最终删除 v1 facade、同步 Agent API、Classic UI 和旧布局兼容。每个 PR 必须独立通过测试和 Ruff。
>
> ## 核心接口与数据模型
>
> - 删除 `SessionStore`、`MemoryStore` 多职责 facade、顶层 `domain.py` 和 `tools.py` 兼容出口。
> - 引入 `WorkspaceDatabase`、`WorkspaceRepositories`、`MemoryDatabase`、`MemoryRepositories`；repository 按 session、workflow、action、source、memory、candidate、embedding 等领域拆分。
> - 所有 repository、模型、工具、动作和工作流接口改为 async；新增 `aiosqlite`，模型客户端改用 `AsyncOpenAI`。
> - 删除同步 `WorkspaceAgent.ask()` 和 `ToolLoop.run()`；保留异步 `ask_stream()`，并保证每次流只产生一个终止事件，不再通过 `last_answer` 传递结果。
> - `ActionCoordinator` 改为异步 handler 注册表。handler 负责文件、命令、Web、MCP 的校验与执行；Coordinator 负责审批、风险、状态转换和审计。
> - `Settings.__getattr__` 删除，调用端显式使用 `model_config`、`runtime`、`command`、`web`、`mcp`、`memory` 配置组。
>
> 工作区 schema 使用独立 SQLite `application_id` 和 v2 schema version。已有表但 application ID 不匹配时拒绝启动，绝不自动删除或覆盖。
>
> - 保留 `sessions`、`messages`、`work_items`、`runs`、`run_steps`、`run_events`、`actions`、`tasks`、`sources`、`tool_calls`、`citations`、settings 和 FTS。
> - 建立完整外键、枚举 `CHECK`、JSON 有效性约束和级联删除规则。
> - `runs.work_item_id` 必填；删除循环依赖的 `work_items.current_run_id`，由 runs 查询当前执行。
> - `run_events` 只保存 `run_id + sequence + kind + payload`，session/work item 从 run 关系获得。
> - `actions` 使用统一的 `request_json` 和 `result_json`，删除三个 action subtype 表；新增动作类型不再要求 schema 迁移。
> - workflow 状态转换采用 compare-and-set，并在单事务内更新 run、work item、action 和终止事件。
>
> 记忆 schema 改为 identity + immutable revision：
>
> - `memories` 保存身份、作用域、状态和当前 revision。
> - `memory_revisions` 保存内容、类型、置信度、过期时间、来源和操作。
> - candidates、extractions、sources、embeddings、recalls、settings、audit 和 FTS 分表并添加约束。
> - purge 删除 revision 正文、FTS、向量和来源，只保留无正文 identity 与审计记录。
> - 新记忆导出使用 `capslock-memory-export` version 3，只接受 version 3 导入；旧 v1/v2 明确拒绝。
> - 会话导出升级为 version 2，不提供旧会话导入或转换。
>

> 采用多 PR 渐进交付。过渡期允许新旧实现并存，但最终删除 v1 facade、同步 Agent API、Classic UI 和旧布局兼容。每个 PR 必须独立通过测试和 Ruff。
>
> ## 核心接口与数据模型
>
> - 删除 `SessionStore`、`MemoryStore` 多职责 facade、顶层 `domain.py` 和 `tools.py` 兼容出口。
> - 引入 `WorkspaceDatabase`、`WorkspaceRepositories`、`MemoryDatabase`、`MemoryRepositories`；repository 按 session、workflow、action、source、memory、candidate、embedding 等领域拆分。
> - 所有 repository、模型、工具、动作和工作流接口改为 async；新增 `aiosqlite`，模型客户端改用 `AsyncOpenAI`。
> - 删除同步 `WorkspaceAgent.ask()` 和 `ToolLoop.run()`；保留异步 `ask_stream()`，并保证每次流只产生一个终止事件，不再通过 `last_answer` 传递结果。
> - `ActionCoordinator` 改为异步 handler 注册表。handler 负责文件、命令、Web、MCP 的校验与执行；Coordinator 负责审批、风险、状态转换和审计。
> - `Settings.__getattr__` 删除，调用端显式使用 `model_config`、`runtime`、`command`、`web`、`mcp`、`memory` 配置组。
>
> 工作区 schema 使用独立 SQLite `application_id` 和 v2 schema version。已有表但 application ID 不匹配时拒绝启动，绝不自动删除或覆盖。
>
> - 保留 `sessions`、`messages`、`work_items`、`runs`、`run_steps`、`run_events`、`actions`、`tasks`、`sources`、`tool_calls`、`citations`、settings 和 FTS。
> - 建立完整外键、枚举 `CHECK`、JSON 有效性约束和级联删除规则。
> - `runs.work_item_id` 必填；删除循环依赖的 `work_items.current_run_id`，由 runs 查询当前执行。
> - `run_events` 只保存 `run_id + sequence + kind + payload`，session/work item 从 run 关系获得。
> - `actions` 使用统一的 `request_json` 和 `result_json`，删除三个 action subtype 表；新增动作类型不再要求 schema 迁移。
> - workflow 状态转换采用 compare-and-set，并在单事务内更新 run、work item、action 和终止事件。
>
> 记忆 schema 改为 identity + immutable revision：
>
> - `memories` 保存身份、作用域、状态和当前 revision。
> - `memory_revisions` 保存内容、类型、置信度、过期时间、来源和操作。
> - candidates、extractions、sources、embeddings、recalls、settings、audit 和 FTS 分表并添加约束。
> - purge 删除 revision 正文、FTS、向量和来源，只保留无正文 identity 与审计记录。
> - 新记忆导出使用 `capslock-memory-export` version 3，只接受 version 3 导入；旧 v1/v2 明确拒绝。
> - 会话导出升级为 version 2，不提供旧会话导入或转换。
>
> ## 分阶段实施
>
> 1. **PR 1：v2 契约与数据库基础**
>
>    新增分领域 domain 类型、异步数据库基类和两套 v2 schema。配置 `foreign_keys=ON`、WAL、busy timeout，完成 application ID 检查、空库初始化和旧库拒绝错误。此阶段新实现可暂不接入主程序。
>
> 2. **PR 2：Repository 与工作流边界**
>
>    拆分 `storage/repositories.py`，引入组合式 repository bundle。实现 `WorkflowService` 的 enqueue、start/resume、complete、fail、cancel、settle-approval 操作。删除 runtime、CLI、session manager 中所有 `_connection` 访问；审批结算必须单事务且可重复调用。
>
> 3. **PR 3：异步动作执行**
>
>    实现 `ActionHandler` 协议和统一状态机。命令使用 `asyncio.create_subprocess_exec`，Web 使用 `httpx.AsyncClient`，MCP 保持原生异步；文件操作放入线程并保持路径、哈希和审批校验。取消命令时先终止进程组，2 秒后强制结束，并将 action/run/work item 一致标记为 cancelled。
>
> 4. **PR 4：异步运行时与工具循环**
>
>    将 runtime 拆为 agent、runner、context、tool loop、events。工具注册表统一 async invoke；文件读取放入线程，Git 使用异步子进程。Skill 加载、上下文构造、候选提取、引用解析和 checkpoint 接入新的 runner。删除同步循环及 MCP 特例分支。
>
> 5. **PR 5：记忆模块拆分**
>
>    拆出 lifecycle、recall、candidates、transfer、validation 和 storage repositories。候选提取和协调使用异步 ChatModel；FastEmbed 放入线程，本地 HTTP embedding 使用 AsyncClient。保持现有作用域、召回权重、4 KiB/top-5 限制和安全过滤语义。
>
> 6. **PR 6：CLI/TUI 收敛**
>
>    `main()` 保留为 `asyncio.run(async_main())` 的控制台包装。顶层只保留默认 TUI、`exec`、`resume`、`sessions`、`doctor`；删除 `chat`、`ask`、`migrate-layout` 和 Classic UI。非 TTY 调用默认入口返回错误并提示使用 `exec`。
>
>    TUI 保留 `/help`、`/status`、`/permissions`、`/approvals`、`/queue`、`/memory`、`/skills`、`/sources`、`/mcp`、`/diff`、`/undo`、`/rename`、`/exit`。删除旧 alias 以及独立的 cost/context/tasks/changes/commands/web 命令，相关信息并入 status 或 approvals。
>
>    render 层按 workflow、action、memory、session、diagnostics 拆分，只接收 typed view model，不访问 Agent 或 repository。
>
> 7. **PR 7：v1 清理与文档**
>
>    删除所有过渡 adapter、旧 schema 迁移、LayoutMigrator、旧路径自动发现和兼容导出。布局只接受 `.capslock/` 与用户 canonical 路径；发现旧路径时列出冲突路径和手动备份/重建指引。更新 README、架构文档、Agent reference 和发布迁移说明。
>
> ## JSONL v2
>
> `capslock exec --json` 每行固定包含 `schema_version=2`、sequence、timestamp、session_id、work_item_id、run_id、event、status、terminal、data。
>
> - completed、waiting_approval、failed、cancelled 是 terminal 事件。
> - completed data 包含 answer、citations、memory recalls、usage 和 duration。
> - waiting_approval 包含 action IDs；failed/cancelled 包含稳定 error code 和 message。
> - 保持退出码：成功 `0`、一般错误 `1/2`、等待审批 `3`、用户取消 `130`。
>

>
> - 空库初始化、application ID、外键、JSON/CHECK 约束及旧库/旧布局拒绝测试。
> - workflow 全状态转换、非法转换、审批结算幂等性和事务回滚注入测试。

> - 本轮不保证现有 SQLite、memory v1/v2 导出或 session v1 导出可迁移，但绝不静默删除用户数据。

> - 旧布局检测只报错和给出手动处理说明，不提供自动迁移或自动重建。
> - 本计划完成代码与文档重构，不包含发布 v2 tag、构建发行包或执行真实用户数据清理。

CapsLock 的会话管理通过 `capslock sessions` 完成。

```bash
# 列出最近会话
capslock sessions

# 增加显示数量
capslock sessions --limit 50

# 搜索标题和对话内容
capslock sessions search "数据库迁移"

# 搜索时包含已归档会话
capslock sessions search "数据库迁移" --archived
```

可以使用完整 Session ID，也可以使用唯一 ID 前缀：

```bash
# 重命名
capslock sessions rename 57a502ca "EWC 赛程查询"

# 归档，默认列表不再显示
capslock sessions archive 57a502ca

# 恢复归档
capslock sessions unarchive 57a502ca

# 导出会话
capslock sessions export 57a502ca exports/ewc-session
```

永久删除历史记录：

```bash
# 交互确认后删除
capslock sessions delete 57a502ca

# 跳过确认
capslock sessions delete 57a502ca --yes
```

删除会永久移除该会话的消息、run、工具调用、引用、动作和 session 作用域记忆。处于运行中或等待审批状态的会话必须先取消相关任务，之后才能删除。

TUI 内可以使用 `/rename <标题>` 重命名当前会话，使用 `/quit` 或 `/exit` 退出；删除操作需要在终端通过 `capslock sessions delete` 执行。
