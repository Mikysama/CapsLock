# 对比工具系统设计并提出优化

> 对比claude code和capslock的工具系统的设计，看capslock的工具系统在哪些方面是可以优化的？（本地有claude code源码，路径/home/lymzhao/workspace/claude-code-src/））

>
> 有两个比较关键的实现事实已经确认：
>
> - CapsLock 的 `interrupt_behavior`、`external_side_effects`、`required` 等字段目前主要被记录，并没有进入实际调度/权限决策；这会形成“接口看起来支持、运行时却不兑现”的语义落差。
> - CapsLock 在工具已成功产生副作用后，如果结果超过硬上限，会把该次调用改写成失败；这会让模型误判“操作没发生”，属于优先级很高的一致性风险。

## 结论

CapsLock 的工具系统并不缺“安全骨架”，甚至在持久化审批、文件变更校验、可撤销操作、插件沙箱和审计方面比 Claude Code 更规整。主要差距在于：

> CapsLock 目前更像“声明式工具目录 + 审批动作系统”；Claude Code 更像“输入感知、可流式、可中断、动态发现的工具运行时”。

CapsLock 最值得优先优化的不是继续增加字段，而是让已有字段真正参与执行，并补齐完整的工具生命周期。

## 核心对比

| 维度 | CapsLock | Claude Code |
|---|---|---|
| 工具契约 | 简洁、协议中立，但能力大多是静态布尔值 | `isReadOnly(input)`、`isConcurrencySafe(input)`、`isDestructive(input)`、`validateInput`、`checkPermissions` 都可按输入判断 |
| 权限 | 以 ActionType 和三种全局模式为主，审批记录持久化 | allow/ask/deny 规则、来源、输入 matcher、hook、用户修改输入、决策原因 |
| 调度 | 模型返回完整批次后，按静态标签分批并发 | 工具调用流式到达即入队；输入感知并发；进度实时回传；兄弟任务取消 |
| 结果 | JSON 文本、单工具大小限制、artifact | 富内容块、MCP structuredContent、进度、聚合上下文预算、稳定预览 |
| 扩展 | 插件沙箱和 capability broker 很强，但启动时静态加载、每次调用启动进程 | MCP 长连接、动态 `tools/list`、重连、原生 schema、进度和 elicitation |
| 审计与安全 | Action 状态机、文件 hash、revalidate、undo 很强 | 权限细，但工具接口和上下文明显更复杂、更耦合 |

Claude Code 的输入感知工具契约集中在 [Tool.ts](~/workspace/claude-code-src/src/Tool.ts:362)；CapsLock 当前对应的是静态的 [ToolCapabilities](./capslock/tooling/async_core.py:25)。

## P0：建议最先处理

### 1. 让 ToolSpec 成为真正的运行时契约

CapsLock 已声明 `interrupt_behavior`、`destructive`、`external_side_effects`、`required` 等元数据，但执行链实际只在并发分批时使用了少数字段：[tool_loop.py](./capslock/runtime/tool_loop.py:630)。

建议引入输入感知的解析阶段：

```python
policy = await tool.resolve_policy(arguments, context)
# policy:
# read_only, concurrency_safe, destructive,
# external_side_effects, interrupt_behavior,
# required_capabilities, timeout
```

然后同一份 `ResolvedToolPolicy` 同时用于：

- 权限判定
- 并发调度
- 中断行为
- UI 风险提示
- 审计记录
- 插件 capability 校验

静态 `ToolCapabilities` 可以保留为默认值，但允许工具按参数收紧权限。尤其是 MCP、命令工具，同一个工具不同输入的风险不可能始终相同。

插件工具目前创建 `Tool` 时没有传 capabilities：[plugins.py](./capslock/tooling/plugins.py:42)。虽然 Action 层仍会审批，但工具元数据、调度和审计看到的风险是不完整的。

### 2. 建立完整、必然收尾的工具状态机

当前 `ToolRegistry.invoke` 只捕获少数异常：[async_core.py](./capslock/tooling/async_core.py:177)。超时、取消、未知运行时异常或并发 `TaskGroup` 失败时，可能直接中断整批调用，并留下未完成的 invocation/step。

建议明确状态：

```text
received → parsed → validated → authorized
         → queued → executing → succeeded/failed/cancelled
         → result_stored → delivered
```

执行器应保证：

- 每个 tool call 都产生一个合法 tool result，包括取消和内部异常；
- invocation 和 step 始终在 `finally` 中收尾；
- 区分 `validation_error`、`permission_denied`、`timeout`、`cancelled`、`execution_error`、`result_delivery_error`；
- 普通工具失败不自动取消所有并行读取；只有明确的 fail-fast policy 才取消兄弟任务；
- 分别记录 queue、approval wait、execution、serialization 时间。

Claude Code 的执行链把 schema 校验、工具专属校验、hook、权限、调用和结果处理拆开了，可参考 [toolExecution.ts](~/workspace/claude-code-src/src/services/tools/toolExecution.ts:614)。

### 3. 修正“大结果导致已执行操作被报告为失败”

CapsLock 当前先执行工具，随后如果结果超过 `max_result_bytes`，会把结果改为 `ok: false`：[tool_loop.py](./capslock/runtime/tool_loop.py:246)。

如果工具已经写文件、发请求或执行第三方操作，模型会误以为操作没有发生并可能重试，这是严重的一致性风险。

建议拆分：

```text
execution_status = succeeded
delivery_status  = artifact_stored | previewed | truncated | failed
```

无论结果多大，都不能改变已经发生的执行事实。超过 inline 限制时直接存 artifact；超过硬限制时保存受限预览并标记 `result_truncated`，而不是把调用变成执行失败。

同时增加“整条消息/整个上下文”的聚合工具结果预算，而不只是每个工具单独 16KB。Claude Code 已维护跨轮次稳定的替换决策，避免破坏 prompt cache：[toolResultStorage.ts](~/workspace/claude-code-src/src/utils/toolResultStorage.ts:367)。

### 4. 真正实现 interrupt_behavior

CapsLock 的取消目前主要是直接取消整个 RunEngine task：[engine.py](./capslock/runtime/engine.py:62)，`InterruptBehavior` 本身没有参与决策。

建议为每次调用建立独立 cancellation scope：

- `cancel`：立即取消并返回合成的 cancelled tool result；
- `complete`：不再启动后续调用，但等待当前调用完成；
- `shield`：关键提交阶段不可取消，完成后再响应用户中断。

默认值也不应一律是 `CANCEL`：只读工具可默认 cancel，有副作用工具应默认 complete/block，由工具显式标注安全取消点。

Claude Code 已按工具行为处理用户新消息和取消：[StreamingToolExecutor.ts](~/workspace/claude-code-src/src/services/tools/StreamingToolExecutor.ts:219)。

## P1：第二阶段优化

### 5. 在 Action 审批之上增加细粒度权限规则

CapsLock 当前权限主要按 ActionType 分成低、中、高风险：[permissions.py](./capslock/permissions.py:41)。建议增加：

- `allow / ask / deny`
- user / project / local / session / policy 来源
- 工具名与输入 matcher
- 工作目录、路径、命令模板、网络 host、MCP server/tool 范围
- 决策原因和“本次允许/始终允许”
- 子 Agent 无法弹窗时的明确降级策略

不要替换 ActionCoordinator。它的持久化审批、重新校验和文件撤销很有价值，特别是文件 hash 防并发修改：[files.py](./capslock/application/action_system/files.py:123)。

推荐链路是：

```text
schema/tool validation
→ permission rule decision
→ durable ActionRecord
→ approval（如需要）
→ revalidate
→ execute
```

### 6. 把 MCP 工具转换为原生 Tool，而不是通用 propose_mcp_call

CapsLock 目前只给模型一个：

```text
server + tool + arbitrary arguments object
```

这丢失了 MCP 工具自身的参数 schema、只读/破坏性 annotation、描述和返回类型。

建议 MCP 连接后：

- 调用 `tools/list`
- 将每个工具转换为 namespaced `Tool`
- 保留实际 input/output schema
- 读取 readOnly/destructive/openWorld annotations
- 原子刷新 ToolCatalog
- 断线时移除或标记 unavailable
- allowed_tools 继续作为上限策略

Claude Code 的转换逻辑可参考 [client.ts](~/workspace/claude-code-src/src/services/mcp/client.ts:1752)。

### 7. 引入动态工具目录和 schema 预算

CapsLock 在 workspace 打开时一次性组装全部工具：[bootstrap.py](./capslock/bootstrap.py:141)，之后每个模型请求发送全部 schema：[tool_loop.py](./capslock/runtime/tool_loop.py:90)。

插件/MCP 增多后会带来：

- prompt token 增长
- prompt cache 不稳定
- 模型选错工具概率上升
- 插件启停必须重开 session

建议实现：

- `ToolCatalogSnapshot(generation, fingerprint, tools)`
- core tools 始终加载
- 大型插件/MCP 工具 deferred loading
- `search_hint` 和 ToolSearch
- 已发现工具集合随会话及 compaction 持久化
- 工具按稳定顺序输出，保证 prompt-cache 前缀稳定

Claude Code 的动态发现机制见 [toolSearch.ts](~/workspace/claude-code-src/src/utils/toolSearch.ts:525)。

### 8. 支持流式进度和富结果

CapsLock 的 ToolResult 最终只能投影成 JSON 字符串：[async_core.py](./capslock/tooling/async_core.py:82)。建议扩展为：

- `structured_data`
- text/image/resource content blocks
- progress event
- display summary
- model projection
- audit projection
- artifact references
- MCP `_meta` / structuredContent

工具执行接口可以返回 `AsyncIterator[ToolEvent]`，或由 context 提供 `report_progress()`。这对长命令、MCP、Web、子 Agent 很重要。

### 9. 替换或强化 JSON Schema 校验

自研 validator 目前只支持较小子集：[schema.py](./capslock/tooling/schema.py:14)，而插件 manifest 接受任意 object schema，容易出现“声明给模型的 schema”和本地实际校验能力不一致。

建议：

- 注册工具时校验 schema 本身；
- 使用成熟的 Draft 2020-12 validator，或明确拒绝不支持的关键字；
- 编译并缓存 validator；
- 内部规范 schema 与不同模型 provider 方言分离；
- 对 `oneOf/anyOf/const/pattern/format/$ref` 等建立明确支持矩阵；
- 为所有内置工具真正声明 output schema。

## P2：产品能力与工程体验

如果 CapsLock 的目标是通用 coding agent，还可以继续补：

- 安全的 argv/process 工具，而不是固定的五种命令模板；
- stdout/stderr 流式输出和后台进程管理；
- 基于 ripgrep 的搜索，而不是 Python 遍历并逐文件读取；
- binary/image/PDF/notebook 读取；
- LSP/symbol 工具；
- 每个工具的契约测试、取消测试、权限矩阵测试和并发属性测试。

另外，当前 UI 展示信息集中在硬编码映射中：[presentation.py](./capslock/tooling/presentation.py:10)，插件工具只能退化成通用展示。可以给工具增加协议中立的 presenter/summary contract，但继续由中心层负责脱敏。

## 不建议照搬 Claude Code 的部分

Claude Code 的 `Tool` 接口同时承载执行、权限、搜索、prompt、UI 渲染、分析埋点和结果映射，已经明显成为“大接口”；`ToolUseContext` 也非常庞大。CapsLock 不应复制这种耦合。

更适合 CapsLock 的目标结构是：

```text
ToolContract      schema、描述、版本
ToolPolicy        输入感知能力与权限 matcher
ToolExecutor      调用、进度、取消
ToolPresenter     UI 摘要与安全展示
ToolResultCodec   模型/audit/artifact 投影
ToolMiddleware    hook、审计、指标、策略
```

优先落地顺序建议是：生命周期与收尾 → 大结果一致性 → 中断语义 → 输入感知策略 → 细粒度权限 → MCP 原生化和动态发现。这样能先解决正确性风险，再提升扩展性和模型效率。

> # CapsLock 工具系统优化方案
>
> ## 总体设计
>
> 将现有“静态 ToolRegistry + Action 提案”升级为输入感知、可流式、可中断、动态发现的 Tool Runtime v2，同时保留 CapsLock 的核心优势：持久化 Action、审批、revalidate、undo、插件沙箱和能力 broker。
>
> 执行链统一为：
>
> ```text
> 模型产生调用
> → schema/语义校验
> → 解析输入级能力
> → 权限规则与 Shell 分类器
> → 必要时暂停等待审批
> → 调度执行
> → 流式进度
> → 结果/artifact 编码
> → 持久化并回传模型
> ```
>
> 实施分三阶段；允许破坏 Tool Python API 和插件协议，但数据库与配置执行自动、可回滚的一次性迁移。
>
> ## 公共接口与核心模型
>
> - 用以下接口替换现有 `Tool`、`ToolSpec` 和固定 JSON `ToolResult`：
>
>   ```python
>   ToolContract(
>       name, version, description,
>       input_schema, output_schema,
>       search_hint, deferred,
>       inline_result_bytes, max_capture_bytes,
>   )
>
>   ResolvedToolPolicy(
>       read_only, concurrency_safe, destructive,
>       external_side_effects, open_world,
>       interrupt_behavior, required_capabilities,
>       timeout_seconds, fail_fast,
>   )
>
>   ToolDefinition(
>       contract,
>       validate(arguments, context),
>       resolve_policy(arguments, context),
>       execute(context, arguments, reporter),
>       presenter,
>   )
>
>   ToolOutcome(
>       status,           # succeeded/failed/denied/cancelled/pending_approval
>       executed,         # 是否已经产生执行或副作用
>       data, content, error,
>       evidence, audit_data, external_usage,
>       delivery_status, # inline/artifact/truncated/delivery_failed
>   )
>   ```
>
> - `reporter(ToolEvent)` 负责进度、阶段切换和资源使用事件；最终结果仍由 `execute()` 返回，保证调用只有一个终态。
> - 新增内部类型化 `ToolMiddleware`，固定顺序为 normalize、validate、resolve-policy、authorize、execute、post-success/failure、encode、audit。首期不开放用户脚本或插件 hook。
> - 使用 `jsonschema` Draft 2020-12 校验器；注册时执行 `check_schema` 并缓存 validator，输入和 `ToolOutcome.data` 都在边界校验。
> - 新增 `ToolCatalog`，提供原子 snapshot、generation、schema fingerprint、动态刷新和会话级 discovered-tool 集合。
> - 删除模型侧 `propose_*` 命名。模型调用 `edit_file`、`create_file`、`shell`、`web_search` 等业务工具；Action 创建和审批完全由运行时处理。
> - MCP 工具命名为 `mcp__<server>__<tool>`，插件工具命名为 `plugin__<plugin>__<tool>`；不提供旧名称适配层。
>
> ## 三阶段实施
>
> ### 第一阶段：运行时正确性与结果一致性
>
> - 重写工具执行器为显式状态机：received、validating、authorizing、queued、running、completed/failed/cancelled；所有异常和取消都在 `finally` 中关闭 invocation 和 run step。
> - 普通工具异常转换为类型化 tool result，不再让 `TaskGroup` 意外取消整批调用；仅 `ResolvedToolPolicy.fail_fast` 可触发兄弟任务取消。
> - 调度前解析实际参数，再决定并发。只允许 `read_only && concurrency_safe && !context_mutation` 的调用并发；结果按模型调用顺序提交。
> - 并行任务不再直接写共享 evidence/source/memory 容器；每个 `ToolOutcome` 独立收集，commit 阶段合并。
> - 为每次调用建立独立 cancellation scope：
>
>   - `cancel`：停止执行并生成 cancelled tool result；
>   - `complete`：不启动后续调用，等待当前调用完成；
>   - `shield`：提交阶段不可取消，完成后响应中断。
>
> - 默认只读工具使用 `cancel`；有副作用工具默认 `complete`，必须显式声明才可安全取消。
> - 分离 `execution status` 和 `delivery status`。结果过大、artifact 写入失败或输出截断不得把已成功执行的操作改成失败。
> - 保留单工具 inline 阈值 16 KiB，新增每批工具结果 64 KiB 聚合预算；超限结果生成稳定预览和 content-addressed artifact，选择结果按 tool call id 持久化，恢复和 compaction 后保持字节一致。
> - 增加 text、JSON、image、resource、artifact content block；provider adapter 将其映射到各模型协议。
> - 事件增加 `tool_queued`、`tool_progress`、`tool_permission`、`tool_cancelled`，并分别记录 queue、approval、execution、encoding 时间。
>
> 第一阶段完成标准：任何异常、取消或超限结果都不会留下 running invocation；已经产生的副作用永远不会被模型误报为“未执行”。
>
> ### 第二阶段：权限、动态工具与插件/MCP
>
> - 新增结构化权限规则，来源为：
>
>   - `~/.capslock/permissions.toml`：用户级；
>   - `.capslock/permissions.toml`：项目级、可提交；
>   - `.capslock/local/permissions.toml`：本地私有；
>   - 数据库：session 临时规则。
>
> - 每条规则包含 `behavior=allow|ask|deny`、tool 名和工具专属 constraint；文件使用 path glob，Shell 使用命令/cwd/sandbox/network constraint，MCP 使用 server/tool constraint。
> - 权限合并遵循：hard deny → 任意显式 deny → 任意显式 ask → allow → permission mode 默认行为。显式 ask/deny 不允许被分类器覆盖。
> - `PermissionDecision` 必须记录行为、规则来源、原因、是否修改输入、持久化建议和审批人；等待审批时暂停 run，在恢复后 revalidate Action，再继续同一个 tool invocation。
> - 保留文件 hash、唯一文本替换、安全 undo 和插件 capability broker；`FULL_ACCESS` 也不能绕过 hard deny、路径边界或沙箱不可用检查。

> # CapsLock 工具系统优化方案
>
> ## 总体设计
>
> 将现有“静态 ToolRegistry + Action 提案”升级为输入感知、可流式、可中断、动态发现的 Tool Runtime v2，同时保留 CapsLock 的核心优势：持久化 Action、审批、revalidate、undo、插件沙箱和能力 broker。
>
> 执行链统一为：
>
> ```text
> 模型产生调用
> → schema/语义校验
> → 解析输入级能力
> → 权限规则与 Shell 分类器
> → 必要时暂停等待审批
> → 调度执行
> → 流式进度
> → 结果/artifact 编码
> → 持久化并回传模型
> ```
>
> 实施分三阶段；允许破坏 Tool Python API 和插件协议，但数据库与配置执行自动、可回滚的一次性迁移。
>
> ## 公共接口与核心模型
>
> - 用以下接口替换现有 `Tool`、`ToolSpec` 和固定 JSON `ToolResult`：
>
>   ```python
>   ToolContract(
>       name, version, description,
>       input_schema, output_schema,
>       search_hint, deferred,
>       inline_result_bytes, max_capture_bytes,
>   )
>
>   ResolvedToolPolicy(
>       read_only, concurrency_safe, destructive,
>       external_side_effects, open_world,
>       interrupt_behavior, required_capabilities,
>       timeout_seconds, fail_fast,
>   )
>
>   ToolDefinition(
>       contract,
>       validate(arguments, context),
>       resolve_policy(arguments, context),
>       execute(context, arguments, reporter),
>       presenter,
>   )
>
>   ToolOutcome(
>       status,           # succeeded/failed/denied/cancelled/pending_approval
>       executed,         # 是否已经产生执行或副作用
>       data, content, error,
>       evidence, audit_data, external_usage,
>       delivery_status, # inline/artifact/truncated/delivery_failed
>   )
>   ```
>
> - `reporter(ToolEvent)` 负责进度、阶段切换和资源使用事件；最终结果仍由 `execute()` 返回，保证调用只有一个终态。
> - 新增内部类型化 `ToolMiddleware`，固定顺序为 normalize、validate、resolve-policy、authorize、execute、post-success/failure、encode、audit。首期不开放用户脚本或插件 hook。
> - 使用 `jsonschema` Draft 2020-12 校验器；注册时执行 `check_schema` 并缓存 validator，输入和 `ToolOutcome.data` 都在边界校验。
> - 新增 `ToolCatalog`，提供原子 snapshot、generation、schema fingerprint、动态刷新和会话级 discovered-tool 集合。
> - 删除模型侧 `propose_*` 命名。模型调用 `edit_file`、`create_file`、`shell`、`web_search` 等业务工具；Action 创建和审批完全由运行时处理。
> - MCP 工具命名为 `mcp__<server>__<tool>`，插件工具命名为 `plugin__<plugin>__<tool>`；不提供旧名称适配层。
>
> ## 三阶段实施
>
> ### 第一阶段：运行时正确性与结果一致性
>
> - 重写工具执行器为显式状态机：received、validating、authorizing、queued、running、completed/failed/cancelled；所有异常和取消都在 `finally` 中关闭 invocation 和 run step。
> - 普通工具异常转换为类型化 tool result，不再让 `TaskGroup` 意外取消整批调用；仅 `ResolvedToolPolicy.fail_fast` 可触发兄弟任务取消。
> - 调度前解析实际参数，再决定并发。只允许 `read_only && concurrency_safe && !context_mutation` 的调用并发；结果按模型调用顺序提交。
> - 并行任务不再直接写共享 evidence/source/memory 容器；每个 `ToolOutcome` 独立收集，commit 阶段合并。
> - 为每次调用建立独立 cancellation scope：
>
>   - `cancel`：停止执行并生成 cancelled tool result；
>   - `complete`：不启动后续调用，等待当前调用完成；
>   - `shield`：提交阶段不可取消，完成后响应中断。
>
> - 默认只读工具使用 `cancel`；有副作用工具默认 `complete`，必须显式声明才可安全取消。
> - 分离 `execution status` 和 `delivery status`。结果过大、artifact 写入失败或输出截断不得把已成功执行的操作改成失败。
> - 保留单工具 inline 阈值 16 KiB，新增每批工具结果 64 KiB 聚合预算；超限结果生成稳定预览和 content-addressed artifact，选择结果按 tool call id 持久化，恢复和 compaction 后保持字节一致。
> - 增加 text、JSON、image、resource、artifact content block；provider adapter 将其映射到各模型协议。
> - 事件增加 `tool_queued`、`tool_progress`、`tool_permission`、`tool_cancelled`，并分别记录 queue、approval、execution、encoding 时间。

> 第一阶段完成标准：任何异常、取消或超限结果都不会留下 running invocation；已经产生的副作用永远不会被模型误报为“未执行”。

## 第一优先级

| 建议工具 | 作用 | CapsLock 当前缺口 |
|---|---|---|
| `write_file` | 创建或完整覆盖文件 | 只有 `create_file` 和精确替换 `edit_file` |
| `glob_files` | 使用 `**/*.py` 等模式查找文件 | `list_files.pattern` 只匹配文件名，不是真正的路径 glob |
| `ask_user` | 在运行中向用户提出结构化问题并继续同一 run | 当前只能结束回答或借用权限审批 |

### 1. `write_file`

Claude Code 的 `Write` 可以创建或覆盖文件，并返回完整 diff，见 [FileWriteTool.ts](~/workspace/claude-code-src/src/tools/FileWriteTool/FileWriteTool.ts:56)。

CapsLock 内部其实已经实现了完整内容替换逻辑 [files.py](./capslock/application/action_system/files.py:35)，只是没有暴露为直接工具。因此这是成本最低、收益最高的补充。

建议接口：

```text
write_file(
    path,
    content,
    expected_sha256?,
    summary?
)
```

对于现有文件，要求先通过 `read_file` 获取 hash；继续保留 Action 审批、hash revalidate、diff 和 undo。

### 2. `glob_files`

Claude Code 的 Glob 支持完整 glob pattern、路径范围、截断信息和并发只读执行，见 [GlobTool.ts](~/workspace/claude-code-src/src/tools/GlobTool/GlobTool.ts:26)。

建议：

```text
glob_files(
    pattern,
    path=".",
    limit=100,
    include_hidden=false
)
```

后端使用：

```text
rg --files --glob <pattern>
```

默认遵循 `.gitignore`，返回 `files/count/truncated`。之后可以考虑由它替代能力较弱的 `list_files.pattern`。

### 3. `ask_user`

Claude Code 允许模型在工具循环中询问 1～4 个结构化问题，见 [AskUserQuestionTool.tsx](~/workspace/claude-code-src/src/tools/AskUserQuestionTool/AskUserQuestionTool.tsx:62)。

建议接口：

```text
ask_user(
    questions=[
        {
            question,
            options=[{label, description}],
            multi_select
        }
    ]
)
```

运行时应增加独立的 `pending_input` 状态，不要伪装成 `pending_approval`：

```text
tool invocation 暂停
→ 问题持久化
→ 用户回答
→ 恢复同一个 invocation
→ 回传结构化答案
```

这样模型可以在实现过程中澄清技术选择，而不必提前结束整个 run。

### 4. 代码语义工具组

Claude Code 的 LSP 工具支持 definition、references、hover、symbols、implementation 和 call hierarchy，见 [schemas.ts](~/workspace/claude-code-src/src/tools/LSPTool/schemas.ts:8)。

考虑到“按直接能力命名”的要求，不建议照搬一个通用 `lsp(operation=...)`，而应提供：

```text
find_definition
find_references
inspect_symbol
list_document_symbols
search_workspace_symbols
find_implementations
get_call_hierarchy
```

这些工具应：

- 全部 deferred
- 只读、可并发、默认取消
- 仅在发现对应语言服务器时加入 Catalog
- 返回文件位置、range、symbol kind 和 evidence
- 文件编辑成功后通知 LSP 更新文档状态

首期可以只实现 `find_definition`、`find_references`、`inspect_symbol` 和 `search_workspace_symbols`。

### 5. MCP Resources

Claude Code 除 MCP tools 外，还提供：

- [ListMcpResourcesTool.ts](~/workspace/claude-code-src/src/tools/ListMcpResourcesTool/ListMcpResourcesTool.ts:15)
- [ReadMcpResourceTool.ts](~/workspace/claude-code-src/src/tools/ReadMcpResourceTool/ReadMcpResourceTool.ts:22)

CapsLock 的 MCP manager 当前只调用 `tools/list` 和 `call_tool`，[mcp_runtime.py](./capslock/mcp_runtime.py:34)。

建议增加：

```text
list_mcp_resources(server?)
read_mcp_resource(server, uri)
```

文本资源返回 resource block；二进制资源写入 content-addressed artifact。还应支持 `resources/list_changed`、资源缓存失效和 server/resource 权限约束。

## 第二优先级

### 6. PDF 和 Notebook

Claude Code 的 `Read` 同时支持文本、图片、PDF 和 Notebook，见 [FileReadTool.ts](~/workspace/claude-code-src/src/tools/FileReadTool/FileReadTool.ts:227)。

CapsLock 已经采用独立的 `read_image`，因此建议保持直接能力拆分：

```text
read_pdf(path, pages?)
read_notebook(path, offset?, limit?)
edit_notebook(path, cell_id?, source, mode, cell_type?)
```

`edit_notebook` 参考 Claude Code 的 replace/insert/delete 模型，[NotebookEditTool.ts](~/workspace/claude-code-src/src/tools/NotebookEditTool/NotebookEditTool.ts:30)，但必须接入 CapsLock 的文件 hash、审批、revalidate 和 undo。

### 7. Git Worktree

建议增加：

```text
create_worktree(name?)
exit_worktree(action="keep|remove", discard_changes=false)
```

Claude Code 会让当前会话切换到隔离 worktree，[EnterWorktreeTool.ts](~/workspace/claude-code-src/src/tools/EnterWorktreeTool/EnterWorktreeTool.ts:23)，退出时对未提交文件和额外 commit 做 fail-closed 检查，[ExitWorktreeTool.ts](~/workspace/claude-code-src/src/tools/ExitWorktreeTool/ExitWorktreeTool.ts:30)。

CapsLock 的 Agent snapshot 是文件复制，不是 Git worktree，也不能为主会话提供分支隔离。该工具特别适合大型重构和多 Agent 并行任务。

删除 worktree 必须：

- 明确审批
- 重新检查未提交文件和 commit
- 不允许作用于非本 session 创建的 worktree
- 状态无法确认时拒绝删除

### 8. 细粒度任务工具

当前 `task_list_update` 会先删除 session 的全部任务再重建，语义过重。Claude Code 提供独立 TaskCreate、TaskGet、TaskList、TaskUpdate。

建议逐步替换为：

```text
create_task(subject, description, blocked_by?)
list_tasks(status?)
get_task(task_id)
update_task(task_id, status?, subject?, description?, blocked_by?)
```

这样可以支持依赖关系、owner 和 Agent 分工，也避免修改一个任务时重建整张任务表。

### 9. 异步 Agent 控制

CapsLock 的 CollaborationService 已经具备 `wait`、`cancel` 和状态流能力，但 `delegate_agents` 当前会等待全部子任务结束才返回，[service.py](./capslock/collaboration/service.py:59)。

可以增加：

```text
get_agent_task(task_id, wait=false, timeout?)
stop_agent_task(task_id)
send_agent_message(task_id, message)  # 后续阶段
```

并让 `delegate_agents` 支持 `background=true`。前两个工具可以直接复用当前 `wait/cancel/stream_status` 实现。

## 第三优先级

可按产品方向选择：

- `enter_plan_mode`、`submit_plan`：模型主动进入只读规划并提交计划审批。
- `powershell`：仅在未来支持 Windows 时加入。
- `mcp_authenticate`：支持 HTTP/SSE MCP 和 OAuth 后再加入。
- 浏览器自动化：优先作为插件或 MCP 工具，不建议进入核心常驻工具。
- `schedule_task`、远程 trigger、主动通知：属于助手产品能力，不是编码工具核心。

## 不建议照搬的 Claude Code 工具

以下能力不适合直接加入 CapsLock 核心：

- `ConfigTool`：模型不应自行修改用户模型、权限或安全设置。
- `BriefTool`：CapsLock 已有正常响应和事件通道。
- `TeamCreate/TeamDelete`：CapsLock 的有界委派模型更简单、安全。
- `SyntheticOutputTool`：应作为 provider/runtime 内部协议，而非模型业务工具。
- `Sleep/Cron/RemoteTrigger`：除非 CapsLock明确转向常驻主动 Agent。
- 浏览器工具：权限面和外部副作用太大，适合 deferred 插件。

推荐实施顺序为：

```text
write_file
→ glob_files
→ ask_user
→ MCP resources
→ 代码语义工具
→ PDF/Notebook
→ Worktree
→ 细粒度任务与异步 Agent 控制
```

其中 `write_file`、`glob_files` 和 MCP resources 能最大程度复用现有运行时，适合作为下一批直接实现的工具。

> ## 总结
>
> 分三阶段补充直接能力工具，并先完善可持久化暂停/恢复机制。所有工具使用小写直接能力名称，不提供旧工具名兼容层。

> - 阶段三：主会话 Worktree、异步 Agent 控制。
> - Workspace schema `7 → 8`，config `4 → 5`。

> ## 公共接口与状态模型
>
> ### 可恢复工具调用
>
> 将非终态从 `ToolOutcome` 中分离：
>
> ```python
> ToolPause(
>     kind,             # approval | user_input
>     request_id,
>     payload,
>     resume_data,
> )
>
> ToolExecution = ToolOutcome | ToolPause
>
> ToolDefinition(
>     contract,
>     validate,
>     resolve_policy,
>     execute,
>     resume=None,
>     presenter=None,
> )
> ```
>
> - `ToolOutcome` 只表示 succeeded、failed、denied、cancelled。
> - Action 等待审批和 `ask_user` 返回 `ToolPause`，不再伪装成失败结果。
> - invocation、run step、run、work item 增加 `waiting_approval`、`waiting_input`。
> - 暂停时持久化模型消息、剩余 tool calls、参数和 resume data；恢复时继续同一个 run、step、invocation。
> - 交互工具形成调度屏障：之前的调用按序提交，之后的调用生成 cancelled 结果并交给下一次模型决策。
> - Action 审批也迁移到该恢复机制；审批完成后模型继续运行，而不是直接结束 run。
>

结论：确实有些混乱，你对 `lsp_runtime.py`、`mcp_runtime.py` 的质疑成立。但更合适的处理不是把它们移动到 `capslock/runtime/`，而是把 LSP、MCP 分别整理成独立的基础设施子包。

`runtime/` 当前已经有比较明确的语义：模型协议、Agent/Run 编排、ToolLoop、路由、上下文和治理。其公开接口也都是这类对象，见 [runtime/__init__.py](./capslock/runtime/__init__.py:1)，架构文档同样如此定义，见 [v1/current.md](./docs/development/v1/current.md:41)。

LSP/MCP 则负责外部协议、子进程、stdio transport、沙箱、重连和服务发现，属于集成基础设施，不属于 Agent 运行内核。

### 主要问题

1. `runtime` 命名已经失去统一含义

目前同时存在：

- `runtime/`：Agent/模型运行内核
- `lsp_runtime.py`：LSP 客户端和进程池
- `mcp_runtime.py`：MCP 连接管理器
- `action_system/shell_runtime.py`：Shell 沙箱和进程管理
- `tooling/permission_runtime.py`：权限规则和中间件

这些模块不在同一个架构层次。用户看到 `*_runtime.py`，自然会认为它们应该进入 `runtime/`。

从代码看，没有必须把 LSP/MCP 放在包根目录的技术原因，更像是增量开发时增加的扁平模块。

2. LSP 模块承担了过多职责

[LspRuntime](./capslock/lsp_runtime.py:40) 同时负责：

- 语言服务器自动探测
- workspace root 查找
- Bubblewrap/sandbox-exec 构造
- 子进程池和空闲回收
- Content-Length JSON-RPC 编解码
- didOpen/didChange
- 超时、取消、shutdown

例如沙箱构造在 [lsp_runtime.py](./capslock/lsp_runtime.py:178)，协议读写在 [lsp_runtime.py](./capslock/lsp_runtime.py:291)。362 行并不是特别大，但职责跨度已经足够形成独立子系统。

3. Tooling 直接依赖具体基础设施

[tooling/lsp.py](./capslock/tooling/lsp.py:11) 直接导入 `LspRuntime`，[tooling/mcp.py](./capslock/tooling/mcp.py:11) 直接导入 `McpConnectionManager`。

这与文档所说的“runtime/tooling 只依赖中立 ports”不一致。现有边界测试只禁止依赖 `application` 和 `storage`，没有禁止依赖具体集成实现，见 [test_boundaries.py](./tests/test_boundaries.py:116)。

4. MCP 存在两条执行路径

这是当前最需要先修复的问题。

正常路径通过长连接管理器：

- [McpConnectionManager.call()](./capslock/mcp_runtime.py:115)
- [McpStdioExecutor.execute()](./capslock/application/action_system/executors.py:98)

但当 manager 缺失时，执行器仍会自行创建一次性 stdio 连接，见 [executors.py](./capslock/application/action_system/executors.py:113)。

同时 `McpActionHandler` 又创建了一份独立 `McpRegistry`，见 [external.py](./capslock/application/action_system/external.py:196)，而 bootstrap 已经为长连接 manager 创建了另一份 registry，见 [bootstrap.py](./capslock/bootstrap.py:182)。

这会导致 allowed-tools、cwd、配置刷新、重连、取消和错误处理出现两套语义。

5. Shell 已经出现真实重复实现

`assess_shell()` 和 `ShellAssessment` 同时定义在：

- [shell.py](./capslock/shell.py:15)
- [shell_runtime.py](./capslock/application/action_system/shell_runtime.py:24)

而且两份规则已经有差异。例如根目录版本额外检查 `mkfs`、`fdisk`、`chmod/chown` 等情况。当前 Action handler 使用的是根目录版本，这意味着另一份逐渐成为危险的“看似有效、实际未使用”代码。

当前文件规模：

- `tooling/async_adapters.py`：884 行
- `tooling/async_core.py`：788 行
- `tooling/async_catalog.py`：561 行
- `bootstrap.py`：561 行
