> # CapsLock v1.10.0 开发计划
>
> ## 摘要
>
> v1.10.0 聚焦“运行预算与循环治理”：将当前单一 `max_turns` 硬失败升级为可审计的运行治理层。TUI 使用可续期软限制，`capslock exec` 使用确定性硬预算，并在重复工具调用形成循环前停止。
>
> 开发前先完成并发布当前 v1.9.0 工作树，补齐缺失的 tag/Release；v1.10.0 不与 v1.9.0 生命周期改动混合提交。
>
> ## 实施阶段
>
> 1. **冻结运行治理契约**
>    - 增加 `StopReason`：`max_tool_rounds`、`max_tool_calls`、`max_duration`、`max_tokens`、`max_budget_usd`、`repeated_tool_call`。
>    - 增加可选的 `RunLimits`、`BudgetSnapshot` 和交互/非交互运行模式；`WorkspaceAgent.ask_stream()` 通过可选参数接收，不破坏现有调用。
>    - 工具轮次定义为“一次返回至少一个工具调用的成功模型响应”；同轮多个工具分别计入工具调用总数，provider 重试不增加工具轮次。
>
> 2. **配置和 CLI 兼容迁移**
>    - 配置升至 `config_version = 2`；自动备份并将 `runtime.max_turns` 改为 `runtime.max_tool_rounds`，默认值保持 32。
>    - `CAPSLOCK_MAX_TOOL_ROUNDS` 为新环境变量；`CAPSLOCK_MAX_TURNS` 和旧配置键兼容至 2.0.0，并在校验、Doctor 和 stderr 给出一次弃用提示。
>    - 优先级固定为新环境变量、旧环境变量、新配置键、旧配置键、默认值；同层出现新旧键时新键生效。
>    - `capslock exec` 增加 `--max-tool-rounds`、`--max-tool-calls`、`--max-duration-seconds`、`--max-tokens`、`--max-budget-usd`；参数必须为正数，并只能收紧配置中的 token、费用和轮次限制。
>    - `exec` 至少默认受 32 工具轮次硬限制；其他维度未配置时不设默认上限。
>
> 3. **预算引擎与持久化**
>    - 建立统一治理器，在每次模型请求和工具调用前做原子预检，在完成后更新累计工具轮次、调用数、耗时、token 和费用。
>    - workspace schema 从 v3 升至 v4；增加 run 治理快照、工具调用指纹历史和 `runs.stop_reason`，并支持 `stopped` 工作项/run 状态。
>    - 增加 `budget_updated`、`limit_reached`、`budget_extended` 非终止事件及 `stopped` 终止事件。
>    - v3→v4 迁移前自动备份；从 `run_steps`、`tool_calls`、`model_calls` 和 run 汇总字段回填历史计数。memory schema 保持 v3。
>    - retry、稳定检查点恢复和进程重启沿 `parent_run_id` 累计原 lineage 用量；只允许提高限制，不清零已用额度，也不重放已完成工具或动作。
>
> 4. **TUI 软限制**
>    - 每完成 32 个工具轮次暂停，显示轮次、工具调用、token、费用、耗时、限额和剩余额度。
>    - 用户只能选择“继续 32 轮”或“停止并总结”；继续操作写入 `budget_extended` 审计事件，不改变权限或审批状态。
>    - 停止总结使用一次 `tools=[]` 的模型调用，禁止产生新工具或动作；若模型预算被拒绝或总结失败，仍以原停止原因结束并保存可用的部分输出。
>    - `/status`、计划/队列详情和活动状态展示当前预算、累计用量、扩展次数及停止原因。
>    - 循环检测、取消和审批等待期间不得因软限制确认而自动批准或启动副作用。
>
> 5. **exec 硬预算与结构化退出**
>    - 在启动下一次模型请求或工具调用前检查所有硬预算；时长限制同时约束正在进行的模型/工具等待并复用现有取消清理。
>    - 达到限制后先发出 `limit_reached`，再发出唯一 `stopped` 终止事件；不执行最终总结，也不启动剩余批次中的工具调用。
>    - JSONL 保持 schema version 2 和既有外层字段顺序，新增事件枚举；终止载荷包含 `stop_reason` 和完整 `budget` 快照。
>    - 退出码固定为：成功 `0`、运行错误 `1`、参数/状态错误 `2`、等待审批 `3`、预算或循环停止 `4`、用户取消 `130`。文本和 JSONL 模式必须返回相同原因与退出码。
>
> 6. **循环检测**
>    - 工具名使用注册表规范名称；参数先按现有安全规则脱敏，再以排序键、紧凑 JSON 生成 SHA-256 指纹，原始敏感参数不进入治理记录。
>    - 默认在第三次相同连续调用执行前停止；相同失败调用第三次重试前停止。
>    - 检测长度 2–4 的短周期，模式第三次重复完成前停止；以上阈值在 `[loop_detection]` 中可配置，但最小值为 2。
>    - 参数变化的分页游标、页码、offset、行范围、路径和批量成员形成不同指纹，可正常推进；无进展地重复旧页仍会被识别。
>    - 循环停止统一使用 `repeated_tool_call`，事件中记录模式类型、周期长度、次数和脱敏指纹，不保存敏感原参。
>
> ## 导出与兼容
>
> - portable archive 升至 version 2，新增治理表及停止字段；v1.10 importer 同时接受 v1.9 的 version 1，并为缺失治理数据执行回填。
> - session export 升至 version 3，包含每个 run 的预算快照、lineage 和停止原因；Markdown 摘要标注未完整完成的 run。
> - v1.9 数据迁移失败时事务回滚并保留备份；回滚到 v1.9 必须恢复迁移前数据库和配置备份。
> - 不增加新工具、权限、后台 daemon、退出后续跑、无限运行或非工具语义循环检测。
>
> ## 测试与验收
>
> - 单元测试覆盖所有预算边界、批量工具调用、模型重试、剩余额度计算、软限制扩展和最终无工具总结。
> - 循环测试覆盖连续相同调用、A/B 交替、2–4 长度周期、持续失败，以及分页、递增范围、批量读取等无误报场景。
> - 恢复测试覆盖取消、审批等待、崩溃、稳定检查点、retry 和重启，确认累计用量不减少且副作用不重放。
> - SQLite 测试覆盖 v3→v4 备份、回填、幂等迁移、失败回滚，以及 portable v1 导入/v2 往返。
> - PTY 测试覆盖 TUI 暂停、继续 32 轮、停止总结、窄终端展示和输入阶段取消。
> - JSONL 契约测试覆盖新事件、唯一终止事件、六种停止原因、退出码 4，以及文本/JSONL 一致性。
> - 安全测试确认预算不足或循环命中后不会启动文件、命令、Web、MCP 等新副作用，指纹和日志不泄露敏感参数。
> - 发布门禁执行 Ruff、完整测试、固定评测、仓库检查、构建、Twine、依赖审计、SBOM、wheel 安装冒烟和版本一致性校验。
>
> ## 默认与前置假设
>
> - TUI 初始软限制和每次续期增量均为 32 工具轮次。
> - `exec` 的工具轮次为默认硬限制；工具调用数、时长、token 和费用仅在配置或 CLI 指定后启用。
> - 停止属于独立的 `stopped` 状态，不伪装为普通失败或成功。
> - v1.9.0 必须先完成提交、CI、tag 和 Release，之后才创建 v1.10.0 开发基线。

> # CapsLock v1.10.0 开发计划
>
> ## 摘要
>
> v1.10.0 聚焦“运行预算与循环治理”：将当前单一 `max_turns` 硬失败升级为可审计的运行治理层。TUI 使用可续期软限制，`capslock exec` 使用确定性硬预算，并在重复工具调用形成循环前停止。
>
> 开发前先完成并发布当前 v1.9.0 工作树，补齐缺失的 tag/Release；v1.10.0 不与 v1.9.0 生命周期改动混合提交。
>
> ## 实施阶段
>
> 1. **冻结运行治理契约**
>    - 增加 `StopReason`：`max_tool_rounds`、`max_tool_calls`、`max_duration`、`max_tokens`、`max_budget_usd`、`repeated_tool_call`。
>    - 增加可选的 `RunLimits`、`BudgetSnapshot` 和交互/非交互运行模式；`WorkspaceAgent.ask_stream()` 通过可选参数接收，不破坏现有调用。
>    - 工具轮次定义为“一次返回至少一个工具调用的成功模型响应”；同轮多个工具分别计入工具调用总数，provider 重试不增加工具轮次。
>
> 2. **配置和 CLI 兼容迁移**
>    - 配置升至 `config_version = 2`；自动备份并将 `runtime.max_turns` 改为 `runtime.max_tool_rounds`，默认值保持 32。
>    - `CAPSLOCK_MAX_TOOL_ROUNDS` 为新环境变量；`CAPSLOCK_MAX_TURNS` 和旧配置键兼容至 2.0.0，并在校验、Doctor 和 stderr 给出一次弃用提示。
>    - 优先级固定为新环境变量、旧环境变量、新配置键、旧配置键、默认值；同层出现新旧键时新键生效。
>    - `capslock exec` 增加 `--max-tool-rounds`、`--max-tool-calls`、`--max-duration-seconds`、`--max-tokens`、`--max-budget-usd`；参数必须为正数，并只能收紧配置中的 token、费用和轮次限制。
>    - `exec` 至少默认受 32 工具轮次硬限制；其他维度未配置时不设默认上限。
>
> 3. **预算引擎与持久化**
>    - 建立统一治理器，在每次模型请求和工具调用前做原子预检，在完成后更新累计工具轮次、调用数、耗时、token 和费用。
>    - workspace schema 从 v3 升至 v4；增加 run 治理快照、工具调用指纹历史和 `runs.stop_reason`，并支持 `stopped` 工作项/run 状态。
>    - 增加 `budget_updated`、`limit_reached`、`budget_extended` 非终止事件及 `stopped` 终止事件。
>    - v3→v4 迁移前自动备份；从 `run_steps`、`tool_calls`、`model_calls` 和 run 汇总字段回填历史计数。memory schema 保持 v3。
>    - retry、稳定检查点恢复和进程重启沿 `parent_run_id` 累计原 lineage 用量；只允许提高限制，不清零已用额度，也不重放已完成工具或动作。
>
> 4. **TUI 软限制**
>    - 每完成 32 个工具轮次暂停，显示轮次、工具调用、token、费用、耗时、限额和剩余额度。
>    - 用户只能选择“继续 32 轮”或“停止并总结”；继续操作写入 `budget_extended` 审计事件，不改变权限或审批状态。
>    - 停止总结使用一次 `tools=[]` 的模型调用，禁止产生新工具或动作；若模型预算被拒绝或总结失败，仍以原停止原因结束并保存可用的部分输出。
>    - `/status`、计划/队列详情和活动状态展示当前预算、累计用量、扩展次数及停止原因。
>    - 循环检测、取消和审批等待期间不得因软限制确认而自动批准或启动副作用。
>
> 5. **exec 硬预算与结构化退出**
>    - 在启动下一次模型请求或工具调用前检查所有硬预算；时长限制同时约束正在进行的模型/工具等待并复用现有取消清理。
>    - 达到限制后先发出 `limit_reached`，再发出唯一 `stopped` 终止事件；不执行最终总结，也不启动剩余批次中的工具调用。
>    - JSONL 保持 schema version 2 和既有外层字段顺序，新增事件枚举；终止载荷包含 `stop_reason` 和完整 `budget` 快照。
>    - 退出码固定为：成功 `0`、运行错误 `1`、参数/状态错误 `2`、等待审批 `3`、预算或循环停止 `4`、用户取消 `130`。文本和 JSONL 模式必须返回相同原因与退出码。
>
> 6. **循环检测**
>    - 工具名使用注册表规范名称；参数先按现有安全规则脱敏，再以排序键、紧凑 JSON 生成 SHA-256 指纹，原始敏感参数不进入治理记录。
>    - 默认在第三次相同连续调用执行前停止；相同失败调用第三次重试前停止。
>    - 检测长度 2–4 的短周期，模式第三次重复完成前停止；以上阈值在 `[loop_detection]` 中可配置，但最小值为 2。
>    - 参数变化的分页游标、页码、offset、行范围、路径和批量成员形成不同指纹，可正常推进；无进展地重复旧页仍会被识别。
>    - 循环停止统一使用 `repeated_tool_call`，事件中记录模式类型、周期长度、次数和脱敏指纹，不保存敏感原参。

CapsLock 的“提案”是受控副作用机制：模型不能直接改文件、执行命令、联网或调用 MCP，而是先创建一条 Action 提案。

基本流程：

1. 模型调用 `propose_file_edit`、`propose_command` 等工具。
2. CapsLock 校验路径、内容、命令模板、URL 或 MCP allowlist。
3. 保存 `pending` Action，并记录风险、请求参数、文件 diff 和回滚说明。
4. 根据权限模式等待人工审批或自动执行。
5. 执行前再次校验，避免文件在提案后被修改。
6. 状态依次为 `pending → approved → running → completed/failed/cancelled`，也可以从 `pending` 进入 `rejected`。

支持的提案包括：

- 文件编辑、文件创建
- 固定模板命令
- Web 搜索、URL 抓取
- MCP 连接、MCP 工具调用

### 如何查看和处理

在 TUI 中执行：

```text
/approvals
```

它会展示当前会话所有 `pending`、`approved`、`running` 提案，包括：

- Action ID
- 风险级别
- 类型和状态
- 摘要
- 脱敏后的完整请求参数
- 文件提案中的 `diff`、目标路径和预期文件哈希

批准或拒绝：

```text
/approvals approve <action-id或唯一前缀>
/approvals reject <action-id或唯一前缀>
```

批准时还会再次显示内容并要求输入 `y` 确认。

### `/diff` 的区别

```text
/diff
```

显示的是当前 Git 工作区已经产生的实际差异，不是专门的待审批列表。未执行的文件提案应通过 `/approvals` 查看；批准执行后才能在 `/diff` 中看到实际变化。

已执行的文件动作可以尝试撤销：

```text
/undo
```

只有文件内容自 CapsLock 执行后未再变化时才允许安全撤销。

### 查看历史提案

`/approvals` 只显示活跃提案。已完成、拒绝或失败的历史 Action 可以导出会话后查看：

```bash
capslock sessions export <session-id> exports/session
```

生成目录中的 `session.json` 包含该会话的 `actions`、状态、请求和结果审计记录。

权限策略可通过以下命令查看或切换：

```text
/permissions
/permissions full
/permissions approve
/permissions ask
```

默认 `approve_for_me` 会要求审批文件、命令和 MCP 等高风险动作；`ask_for_approval` 审批所有动作；`full_access` 可自动执行，但 Skill 文件修改仍必须逐次确认。
