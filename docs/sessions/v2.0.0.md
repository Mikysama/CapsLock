> # CapsLock v2.0.0 开发计划
>
> ## 总体目标
>
> 2.0.0 定位为“稳定个人 Agent”发布，不新增插件市场、远程控制、多 Agent 或多模态能力，重点完成：
>
> - 公共接口和数据协议冻结。
> - 1.10.1 标记的弃用接口彻底删除。
> - 升级、回滚、恢复和安全边界验证。
> - 安装、核心功能和端到端质量达到正式发布标准。
> - 建立明确的平台支持矩阵、迁移文档和发行候选流程。
>
> 当前基线：Python 3.11 环境下 `159 passed`，Ruff 检查通过；Agent 确定性评测和记忆评测均为 `1.0`。现有默认 `.venv` 缺少 `tomlkit`，不能作为发布验证环境，后续统一使用干净安装环境。
>
> ## 实施阶段
>
> ### 1. 兼容契约冻结与接口清理
>
> 以 `docs/development/v2.md` 和 `docs/roadmap.md` 为唯一规范，建立 v2 公共契约清单，覆盖 CLI、配置、数据库、归档、事件、Skill manifest、工具结果和 Python API。
>
> 删除 1.10.1 弃用入口：
>
> - `RunContext(repositories=...)`，只保留 `tasks=`、`sources=` 等窄端口。
> - `ToolLoop(repositories=...)`，只保留 `journal=`。
> - `ModelRouter(repositories=...)`，只保留 `audit=`。
> - `ModelRouter.bind_run()`、`use_role()`、`summary(run_id)`，统一改用 `ModelRunSession`。
> - `max_turns` 构造参数、配置键、环境变量和兼容常量，统一使用 `max_tool_rounds`。
>
> 同步清理 v2 架构文档中列出的不兼容出口：
>
> - `SessionStore`、`MemoryStore`、上层 `_connection` 访问。
> - 同步 `WorkspaceAgent.ask()` 和同步 ToolLoop。
> - `WorkspaceAnswer`、`last_answer`。
> - `LayoutMigrator` 和旧布局自动发现。
> - Classic UI、`chat`、`ask`、`migrate-layout`。
> - 顶层旧 `capslock.domain`、`capslock.tools` 兼容出口。
> - 旧 memory/session export import 格式。
>
> 旧配置不再静默兼容：发现 `max_turns` 或 `CAPSLOCK_MAX_TURNS` 时直接返回带迁移指引的配置错误，不能继续运行。
>
> ### 2. 升级、回滚与恢复保障
>
> 保持 v2 既定协议不变：
>
> - workspace application ID、memory application ID 不变。
> - 1.10.0 的 workspace schema v4、memory schema v3 不新增 v2.0 专用迁移。
> - portable archive v2、JSONL schema v2、退出码和权限模式保持兼容。
> - canonical `.capslock/` 布局保持不变。
>
> 新增升级测试矩阵：
>
> - `1.10.0 -> 2.0.0`：配置、workspace 数据库、memory 数据库、归档和运行事件。
> - `1.10.1 -> 2.0.0`：验证无损启动和无副作用迁移。
> - 已完成、失败、取消、等待审批、导入中的 run。
> - schema/application ID 错误、迁移中断、备份损坏、恢复失败。
> - 回滚前自动生成备份，恢复后数据、权限状态和审计事件保持一致。
> - 重复升级、重复恢复和重复导入必须幂等。
>
> 补充升级文档，逐项列出旧 API 到新 API 的替换方式，以及 CLI、配置和导出格式的兼容边界。
>
> ### 3. 安全、生命周期和用户文档收口
>
> 更新并统一以下文档：
>
> - `README.md`：安装、支持平台、快速开始、权限模式和安全边界。
> - `docs/agent-reference.md`：CLI、JSONL、工具结果、恢复、记忆和模型降级契约。
> - `docs/development/v2.md`：最终模块边界、删除清单和迁移规则。
> - 新增 v2 升级指南：配置、Python API、CLI、数据备份和回滚步骤。
> - `CHANGELOG.md` 与 `docs/releases/v2.0.0.md`：用户可见变更、已知限制和支持矩阵。
>
> 文档必须明确：
>
> - 支持 Linux/macOS、Python 3.11/3.12。
> - 权限模式、审批、文件/命令/Web/MCP 数据边界。
> - 记忆的查看、修改、导出、删除和跨工作区隔离。
> - 外部模型、Web、MCP 和 embedding 的数据外发规则。
> - 故障恢复、取消、循环停止、预算停止和未完成动作处理。
> - 2.0 的弃用周期：已删除接口不再保留兼容分支，未来新增弃用必须至少提前一个 minor 版本公告。
>
> ### 4. 端到端评测与发布质量门禁
>
> 扩展现有 `scripts/evaluate_agent.py` 和固定 fixture，形成 v2 发布评测套件，至少覆盖：
>
> - 干净安装和 wheel/sdist 安装。
> - 旧版本升级、备份、回滚和恢复。
> - 工作区问答、证据引用和会话恢复。
> - 文件编辑审批、冲突检测和撤销。
> - 固定命令执行、超时、取消、输出限制和预算停止。
> - Web 搜索/抓取、SSRF 防护、来源审计和不可信内容标记。
> - 本地 MCP 连接、工具发现、allowlist、审批和子进程清理。
> - 记忆作用域、候选审核、召回、过期、purge、导入导出和跨工作区隔离。
> - Skill manifest 校验、覆盖/禁用、资源快照和权限边界。
> - 模型重试、同 data-policy 降级、流式失败、预算和费用统计。
> - TUI、JSONL、无颜色模式、窄终端、Ctrl-C 和非交互退出码。
>
> 质量门槛：
>
> - 全量单元/集成/安全测试通过。
> - deterministic Agent evaluation quality 为 `1.0`。
> - memory evaluation 达到现有最低阈值 `0.90`，发布候选目标为 `1.0`。
> - 不允许跨工作区泄露、已删除记忆复现、审批绕过、路径越界或未审计副作用。
> - 运行时、tooling、domain、ports 的静态依赖方向测试通过。
> - 评测依赖缺失时必须报告明确的环境错误，不能产生误导性的 JUnit 解析异常。
>
> ### 5. RC 与正式发布
>
> 建立 RC 流程：
>
> 1. 冻结 CLI、配置、schema、archive、event、Skill 和工具结果协议。
> 2. 完成 API 删除和迁移文档。
> 3. 在 Linux/macOS × Python 3.11/3.12 执行完整 CI。
> 4. 执行 Ruff、pytest、依赖检查、pip-audit、仓库卫生、构建、Twine、版本校验和 wheel 隔离安装。
> 5. 对 RC 运行完整端到端、安全和升级回滚评测。
> 6. 只修复阻断级和高优先级发布缺陷；不再合入新能力。
> 7. 将唯一版本源更新为 `2.0.0`，同步 README、CHANGELOG、发布说明和文档。
> 8. 创建匹配的 `v2.0.0` tag，由 CI 校验 tag、源码版本、构建制品和 GitHub Release 完全一致。
>
> ## 测试计划
>
> 新增或改造以下测试类别：
>
> - API 删除测试：旧构造参数、方法、模块出口和同步入口均不可用。
> - 配置测试：`max_tool_rounds` 正常工作，旧 `max_turns` 明确拒绝。
> - 迁移测试：1.10.0/1.10.1 数据库和配置升级、备份、失败回滚、重复执行。
> - 协议回归测试：CLI 退出码、JSONL schema、archive v2、Skill manifest、工具结果格式。
> - 安全测试：权限模式、敏感信息脱敏、路径边界、SSRF、MCP allowlist、记忆隔离。
> - E2E 测试：覆盖 roadmap 要求的安装、升级、恢复、工作区、Web、MCP、记忆、Skill 和模型降级场景。
> - 发布测试：四个平台/解释器组合、wheel/sdist、仓库外导入和 `capslock --version`。
>
> ## 完成标准与默认假设
>
> - 2.0.0 不提高数据库 schema version，不改变权限模型，不扩大数据范围。
> - 1.10.0 和 1.10.1 是必须支持的最近两个升级来源；更早版本通过已有导出/手工迁移流程处理。
> - 所有删除的 Python API 以显式失败替代静默兼容。
> - 正式发布前不得将 2.1 插件 SDK、2.2 多 Agent 或后台能力混入本版本。
> - 只有全部测试、评测、升级回滚和发布制品门禁通过后，才创建 `v2.0.0`。
>
