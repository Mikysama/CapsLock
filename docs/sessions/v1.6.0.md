> 我会先梳理仓库中的 CapsLock 文档、现有版本历史和 roadmap，再据此确认 v1.6.0 的目标边界、依赖关系与可验收项；这一步只做只读检查，不改动文件。
>
> 目前文档结构很清晰：有总 roadmap、按版本的开发记录、发布说明和会话记录。接下来我会交叉比对 v1.5 已完成内容与 roadmap 中 v1.6 的表述，避免把已落地功能或更远期设想误排进 1.6。
>
> roadmap 已经明确了 v1.6 的产品风险：不是“让模型随意记住更多”，而是在现有手动记忆层上增加可审核的候选、受控采纳和可解释召回。为了把计划做到可直接实施，我还需要核对当前记忆 schema、服务接口、模型工具和 CLI 命令的实际形态，并据此拆出迁移与测试阶段。
>
> 现有实现确认了几个关键约束：记忆是独立的用户级 SQLite（当前 schema v1），已有 revision、来源、置信度、过期时间、FTS 和 run 访问记录；模型目前只能显式调用只读搜索，系统提示还明确禁止推断或写入记忆。因此 v1.6 需要同时演进用户库、运行后处理流程、上下文构建和 `/memory` 管理面，但无需扩大文件/命令/Web/MCP 权限。
>
> 有两处产品决策无法从仓库里唯一推导出来，而且会直接改变 v1.6 的实现范围：`automatic` 到底允许自动采纳哪些候选，以及“外部嵌入提供方”是本版本实装还是只保留受控接口。下面我给出与现有安全原则最一致的默认选项。
>
> 你选择的边界会显著降低 v1.6 的发布风险：每个成功 run 后提取，`automatic` 只处理低风险的用户明确陈述，外部嵌入延后到 1.8。还剩一个实现层选择需要锁定：本地嵌入怎样交付，以及召回解释在 CLI 中默认展示到什么程度。
>
> 方案现在可以按四条主线收敛：schema/provenance、候选提取与审核、混合召回与双本地嵌入后端、安全评测与发布。最后我会核对当前迁移版本和测试基线，让计划中的升级路径、回滚条件和验收数字都建立在现状上。
>
> 当前 shell 没有 `python` 命令，因此直接测试基线无法启动；我会检查仓库虚拟环境或 `python3` 是否可用，再决定是否能补上现有测试数。这个环境问题只影响基线验证，不改变计划内容。

> # CapsLock v1.6.0 开发计划：上下文智能与受控自动记忆
>
> ## 概要
>
> 在 v1.5.1、工作区 schema v5、用户记忆 schema v1 和现有 136 项测试通过的基线上，增加候选提取、审核/自动采纳、可解释召回、来源治理与本地嵌入。默认策略为 `review`，不扩大文件、命令、Web 或 MCP 权限。
>
> 按单人开发估算为 4 个阶段、约 4–5 个工程周；每阶段均应保持主分支可测试、可回滚。
>
> ## 实施阶段
>
> ### 1. 数据模型与策略基础
>
> - 将用户记忆库从 schema v1 升至 v2；迁移前用 SQLite backup API 自动备份，事务失败时回滚，重复启动不重复备份。工作区数据库保持 schema v5。
> - 新增 `MemoryPolicy(off|review|automatic)`、`MemoryCandidateStatus`、`MemoryOrigin`、`MemoryRecallHit` 和 `EmbeddingBackend` 类型。
> - 增加提取记录、候选队列、多来源关系、向量、召回明细和无正文审计表；现有记忆增加 `origin`，保留当前 `source_kind/source_ref` 兼容读取。
> - 将“是否允许写入”和“自动化策略”分离：项目 `[memory] enabled=false` 与本机 `/memory disable` 继续禁止全部写入；`policy=off` 仅关闭提取和自动采纳，显式读取及手动管理仍可用。
> - 默认 `policy=review`、自动召回开启、本地嵌入关闭；所有设置保存在用户级工作区设置中，项目配置不能静默提升为 `automatic`。
> - 过期记忆立即退出 FTS、向量和上下文，但不自动永久删除；失效来源进入审计，自动来源记忆停止召回，人工审核记忆保留但降权并显示警告。
>
> ### 2. 候选提取、审核与采纳
>
> - 每个成功 run 在回答和消息落库后同步执行一次无工具提取；使用当前聊天模型，不引入新的模型提供方，token 与费用计入原 run。提取失败只记录事件，不使主回答失败。
> - 提取输入仅包含有界的当前会话文本；Web、MCP、工具结果、Skill 和助手文本均标记为不可信，候选必须指向具体的用户消息与源 run。
> - 使用严格 JSON 契约提取 `fact/preference/decision/todo`；模型原始输出不进入日志，候选正文必须先通过长度、UTF-8、敏感信息脱敏和作用域校验。
> - 通过规范化匹配、混合检索候选集及一次无工具 reconciliation 调用判断 `new/duplicate/conflict`。解析失败或判断不明确时一律进入人工审核。
> - `review` 只保存待审候选，不修改可信记忆；审核支持编辑后采纳、拒绝、保留现有、替换现有或冲突双方并存。
> - `automatic` 仅自动采纳置信度不低于 0.90、由用户直接陈述、作用域为 workspace/session、无敏感脱敏、无冲突且来源有效的候选；global、note、模型推断和外部事实始终要求审核。
> - 自动重复项只合并来源与审计，不覆盖现有正文；每条自动记忆必须关联 extraction ID、源 run、模型、prompt 版本和实际采用策略。
> - 已采纳候选清除重复正文，拒绝/重复候选正文默认保留 30 天后安全清除；用户可提前 purge，审计只保留无正文元数据。
>
> ### 3. 可解释召回与本地嵌入
>
> - 每轮构建上下文时，从可见、活动、未过期且来源允许的记忆中生成 FTS top-20 与向量 top-20 候选。
> - 相关性占 55%，作用域 15%，置信度 15%，时效 10%，来源有效性 5%；词法与语义排名使用 RRF 融合，缺失向量时自动退化为词法检索。
> - 仅注入总分不低于 0.45 的前 5 条，正文总量不超过 4 KiB；以明确的“不可信记忆数据”系统区块注入，不能作为指令或权限来源。
> - 每轮输出一行召回摘要；`/memory context [run-id]` 展示 ID、总分、词法/语义命中、作用域、置信度、时效和来源状态。
> - 提供两种显式启用的本地嵌入后端：
>   - `fastembed` 作为 `local-embeddings` 可选依赖，默认模型为 `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`；首次下载前显示模型、缓存目录和网络行为并确认。
>   - OpenAI-compatible 本地 HTTP embeddings；只允许解析到 `localhost`、`127.0.0.1` 或 `::1`，禁止重定向和非回环地址。
> - 向量按 memory ID、revision、backend、model 和内容哈希缓存；修改、遗忘、过期、purge 或模型变更时失效。后端故障不得阻断记忆写入或回答，自动退化到 FTS。
> - 外部嵌入实现不进入 v1.6；更新 roadmap，将真实外部 provider、外发数据预览、确认与审计加入 v1.8.0。
>
> ## CLI 与兼容接口
>
> - 新增 `/memory policy off|review|automatic`、`/memory recall on|off` 和增强后的 `/memory status`。
> - 新增 `/memory candidates [pending|all]`、`/memory candidate show|review|reject|purge <id>`、`/memory context [run-id]`、`/memory cleanup`。
> - 新增 `/memory embeddings status|enable fastembed|enable local-http|disable|rebuild`；启用和全量重建均需显式确认。
> - 保留 `/memory enable|disable`、现有手动 CRUD、FTS、引用和 ID 前缀行为。
> - 记忆导出格式升至 v2，增加 origin、provenance，并可选择包含候选；导入继续接受 v1。导入的候选只能成为 pending，不能触发自动采纳。
> - 更新 README、agent reference、v1.6 开发文档、CHANGELOG、发布说明和 downgrade 指引；版本唯一源升级为 `1.6.0`。
>
> ## 测试与验收
>
> - 迁移测试覆盖 v1→v2 备份、幂等、失败回滚、新版本拒绝及恢复 v1 备份。
> - 策略矩阵覆盖项目禁令、本机禁用、三档 policy、召回开关，以及失败 run 不提取。
> - 提取测试覆盖严格解析、敏感信息、提示注入、直接/推断来源、重复、冲突、模型失败、成本统计和完整 provenance。
> - 召回测试覆盖三种作用域、排序解释、4 KiB/top-5 限制、过期、遗忘、purge、来源失效、历史 run 失效和跨工作区隔离。
> - 嵌入测试覆盖两种后端、缓存失效、模型切换、HTTP 回环限制、重定向拒绝、超时降级；可选 extra 在 Linux/macOS、Python 3.11/3.12 安装冒烟。
> - 增加中英文质量评测集：跨工作区泄露、敏感正文持久化、禁止记忆绕过、过期/删除复现必须为 0；召回 top-5 命中率至少 90%，重复/冲突识别率至少 95%。
> - 发布前必须保持现有 136 项回归全部通过，并通过 Ruff、依赖检查与审计、仓库卫生、构建、Twine、wheel 安装、版本一致性及 `v1.6.0` tag 校验。
>
> ## 明确边界
>
> - 不实现外部嵌入、后台任务、定时提醒、远程 MCP、任意 Shell、TUI 或模型路由。
> - 不从网页、MCP、工具结果、Skill 或助手推断中自动建立长期事实。
> - 不自动创建 global 记忆，不自动永久删除记忆正文，不允许记忆内容改变现有权限策略。

> MEMORY_SCHEMA_VERSION = 2是什么

`MEMORY_SCHEMA_VERSION = 2` 是“用户记忆 SQLite 数据库”的结构版本号，不是 CapsLock 产品版本号。

它位于 [capslock/storage/memory.py](./capslock/storage/memory.py:28)，通过 SQLite 的 `PRAGMA user_version` 管理数据库迁移：

- 新建记忆库时直接创建 schema v2。
- 打开 schema v1 时，先备份数据库，再迁移到 v2。
- 迁移失败会回滚并保留备份。
- 数据库版本高于 2 时拒绝启动，避免旧代码破坏新数据。

v2 相比 v1 增加了：

- 记忆来源与 `origin`
- 自动提取记录
- 候选审核队列
- 多来源 provenance
- 本地嵌入向量
- 召回结果与排名原因
- `off/review/automatic` 策略和召回/嵌入设置

它与工作区数据库的 `SCHEMA_VERSION = 5` 相互独立：

```text
用户记忆库 memory.sqlite3       MEMORY_SCHEMA_VERSION = 2
工作区状态 capslock.sqlite3    SCHEMA_VERSION = 5
CapsLock 软件版本              1.6.0
```

CapsLock v1.6.0 的记忆系统采用“独立持久化、作用域隔离、候选审核、按需召回”的设计。它不是简单地把聊天历史全部塞给模型。

**整体架构**

CapsLock 实际维护两类数据：

```text
工作区 SQLite
├─ 会话、消息、run、工具调用
└─ 用作当前会话上下文和审计

用户记忆 SQLite
├─ memories / history / audit
├─ candidates / extractions / sources
├─ FTS5 / embeddings
└─ recall records
```

用户记忆库独立于工作区库，通常位于 `${CAPSLOCK_HOME}/state/memory.sqlite3`。核心记录包含正文、类型、作用域、来源、置信度、过期时间、revision、状态和创建来源，见 [domain.py](./capslock/domain.py:215)。

记忆类型包括：

- `fact`
- `preference`
- `decision`
- `todo`
- `note`

类型描述“内容是什么”，不决定保存时间。

**长短期记忆**

代码里没有直接定义 `SHORT_TERM` 或 `LONG_TERM` 枚举。长短期由“会话上下文、作用域和过期时间”共同表达：

| 层次 | 实现 | 生命周期 |
| --- | --- | --- |
| 工作记忆 | 当前问题、最近消息、压缩摘要 | 当前模型上下文 |
| Session 记忆 | `scope=session` | 只对当前会话可见 |
| Workspace 记忆 | `scope=workspace` | 跨会话、仅当前工作区 |
| Global 记忆 | `scope=global` | 跨会话、跨工作区 |
| 临时记忆 | 任意 scope 加 `expires_at` | 到期后停止检索 |
| 长期记忆 | workspace/global 且无过期时间 | 持续保存，直到用户遗忘或清除 |

因此可以近似理解为：

```text
短期记忆 = 最近对话上下文 + session scope + 有 expires_at 的记录
长期记忆 = workspace/global scope 且没有过期时间
```

但 `session` 记忆在物理上仍写入 SQLite，不会在退出时自动删除；它只是可见范围更窄。真正删除需要 `forget` 或 `purge`。

作用域定义见 [domain.py](./capslock/domain.py:42)，可见性过滤见 [storage/memory.py](./capslock/storage/memory.py:419)。

**记忆写入流程**

成功 run 完成后，CapsLock 使用当前聊天模型执行一次无工具候选提取，见 [runtime.py](./capslock/runtime.py:166)。

提取结果不会立即等同于可信记忆：

```text
用户消息
  → 候选提取
  → 敏感信息过滤
  → 重复/冲突判断
  → pending candidate
  → 人工审核或受限自动采纳
  → trusted memory
```

三种策略：

- `off`：不提取候选。
- `review`：默认，只进入审核队列。
- `automatic`：仅自动采纳用户直接陈述、置信度 ≥ 0.90、无敏感信息、无冲突且属于 workspace/session 的候选。

Global、模型推断、外部工具/Web/MCP 内容始终不能自动成为长期记忆。实现位于 [memory.py](./capslock/memory.py:406)。

重复候选只补充来源，不覆盖正文；冲突候选进入人工审核。每条自动记忆都保留 extraction ID、源 run、模型版本和来源记录。

**记忆召回**

召回发生在调用主模型之前，由 `ContextBuilder` 根据当前问题查询记忆，见 [runtime_support.py](./capslock/runtime_support.py:28)。

流程如下：

```text
当前问题
  ├─ FTS5/LIKE 词法检索 top 20
  └─ 可选向量检索 top 20
          ↓
      合并候选
          ↓
  作用域、置信度、时效、来源评分
          ↓
  阈值过滤、top 5、最大 4 KiB
          ↓
  作为“不可信记忆数据”注入系统上下文
```

词法检索使用 FTS5，并针对中文补充字符片段 LIKE 匹配，见 [storage/memory.py](./capslock/storage/memory.py:443)。

可选语义检索支持：

- 进程内 FastEmbed
- 仅回环地址的 OpenAI-compatible `/embeddings`

嵌入关闭或失败时自动退化为纯词法检索。

最终得分公式是：

```text
score =
  相关性 × 55%
  + 作用域 × 15%
  + 置信度 × 15%
  + 时效 × 10%
  + 来源有效性 × 5%
```

作用域权重：

```text
session   = 1.00
workspace = 0.85
global    = 0.70
```

时效按约 180 天线性衰减。得分低于 `0.45` 的记录不会注入；最多选 5 条，正文合计不超过 4 KiB。具体实现见 [memory.py](./capslock/memory.py:273)。

**召回安全性**

注入模型的内容被包在 `<untrusted-memory-context-json>` 中，并明确声明：

- 记忆可能已经过时。
- 记忆不是系统指令。
- 记忆不能授予工具或文件权限。
- 使用记忆回答时必须输出 `[[memory:mem_...]]` 引用。

每次召回还会保存 memory ID、revision、得分、词法/语义排名和原因，见 [storage/memory.py](./capslock/storage/memory.py:839)。用户可通过 `/memory context` 查看这些信息。

如果一条曾被使用的记忆后来被修改、遗忘、过期或清除，相关旧 run 会被排除出未来对话历史，避免已经失效的记忆通过历史回答重新进入上下文。

> 工作区sqlite存放在哪儿

工作区 SQLite 默认存放在当前项目的：

```text
<workspace>/.capslock/state/capslock.sqlite3
```

例如当前仓库对应：

```text
/home/lymzhao/workspace/CapsLock/.capslock/state/capslock.sqlite3
```

路径由 [layout.py](./capslock/layout.py:120) 定义。这个数据库保存：

- 会话和消息
- run 与 token/费用
- 文件、命令、Web、MCP 动作
- 任务、来源和引用
- 工作区设置与 Skill 状态

它与用户记忆库不同：

```text
工作区状态：<workspace>/.capslock/state/capslock.sqlite3
用户记忆：  ${CAPSLOCK_HOME:-~/.capslock}/state/memory.sqlite3
```

旧版兼容路径 `<workspace>/.capslock/capslock.sqlite3` 仍可读取，但会提示执行 `capslock migrate-layout`。

> capslock是如何决定该记忆可以写进长期记忆中的？

CapsLock 不会让模型直接写入长期记忆。模型只负责提出候选，最终是否写入由固定策略和用户审核决定。

**判断流程**

```text
成功完成的用户 run
  → 模型提取候选
  → 格式与敏感信息校验
  → 重复/冲突判断
  → 应用 off/review/automatic 策略
  → 写入可信记忆或进入审核队列
```

候选提取只允许四种类型：

- `fact`
- `preference`
- `decision`
- `todo`

`note`、助手推断、工具结果、Web/MCP 内容不能自动提取。候选必须声明它是用户直接表达的内容，即 `direct=true`。实现见 [memory.py](./capslock/memory.py:406)。

**三种写入策略**

`off`：

- 不调用提取模型。
- 不生成候选。
- 不自动写入。

`review`，默认：

- 候选只进入审核队列。
- 用户通过 `/memory candidate review <id>` 编辑、确认作用域后才能写入。
- 用户可以在审核时接受为 global、workspace 或 session 记忆。

`automatic`：

只有同时满足以下条件才会自动采纳：

```python
candidate.relation == "new"
candidate.confidence >= 0.90
candidate.scope in {workspace, session}
candidate.risk_flags == ()
```

对应实现见 [memory.py](./capslock/memory.py:616)。

也就是说，自动写入要求：

- 来自一个成功 run 的用户直接陈述。
- 置信度至少为 `0.90`。
- 不包含被脱敏的 token、密钥或其他敏感内容。
- 不是模型推断。
- 不是 global 作用域。
- 没有重复判断失败。
- 没有与现有记忆冲突。

**重复和冲突**

写入前会检索相同类型、相同作用域的现有记忆：

- `new`：没有发现重复或冲突，可继续判断。
- `duplicate`：不覆盖原正文，只给原记忆增加新的来源记录。
- `conflict`：禁止自动写入，进入人工审核。
- 判断失败：添加 `reconciliation_failed` 风险标记，禁止自动写入。

因此模型不能用一条新输出静默覆盖旧记忆。

**什么算长期记忆**

CapsLock 没有单独的 `long_term=true` 字段。长期性由作用域和过期时间决定：

```text
workspace + expires_at=None  → 工作区长期记忆
global + expires_at=None     → 用户全局长期记忆
session                      → 仅当前会话可见
expires_at 有值              → 到期后停止召回
```

自动模式最多只能创建 workspace 或 session 记忆，不能自动创建 global 记忆。自动创建的 workspace 记忆默认没有过期时间，因此会成为“项目级长期记忆”。

真正的全局长期记忆必须由用户：

- `/memory add` 手动创建，或
- 在候选审核时明确接受为 `global`

核心原则是：模型决定“建议记什么”，固定规则决定“能否自动记”，用户决定高风险或全局内容“是否真正成为长期记忆”。
