# 制定v1.8.0开发计划

> 根据capslock相关文档和roadmap，给出v1.9.0版本的开发计划

<details><summary>7 previous messages</summary>

> 我会先梳理仓库里的 CapsLock 文档、版本记录和 roadmap，确认当前实现基线、v1.9.0 已经承诺的范围以及未决依赖；然后再把产品目标和工程落点整理成可直接执行的版本计划。
>
> 仓库目前的公开发布文档到 `v1.8.0`，同时保留了按版本拆分的开发设计文档。我接下来会重点对照 `roadmap`、`v1.8` 设计与发布说明、当前版本总览和实际代码/测试，避免把已经完成的工作重复排进 v1.9.0。
>
> v1.9.0 的范围在 roadmap 中已经明确，但要做到“交给工程师即可实现”，还需要锁定几个关键契约：配置迁移如何落盘、系统凭据存储采用什么抽象、备份包包含哪些数据库及如何校验恢复、`doctor` 的修复边界。我正在把这些目标映射到现有组合根、双 SQLite 所有权和布局迁移机制上。
>
> 这里发现一个会直接影响 v1.9 计划的现状：当前代码自称 “v2 canonical layout”，遇到旧布局、旧 application ID 或未知数据库版本时会拒绝启动，而 roadmap 又要求从 1.3.x 连续升级到 1.9.0。也就是说，本版本不能只新增向导和备份命令，还必须建立一个独立于正常应用启动的迁移/恢复入口，否则旧用户会在配置加载或数据库打开前就被拦住。
>
> 从现有历史可以确认，旧版并不是单一格式：workspace schema 依次经历了 v1/v2/v3/v5/v6，记忆库也有独立版本；当前 fresh-v2 又换了 application ID 和严格表结构。因此迁移会按“识别旧格式 → 一致性备份 → 在临时目录构建新库并做逻辑转换 → 完整性校验 → 原子切换”设计，而不是尝试在原文件上跨代执行 SQL。这样才能同时满足回滚和审计链保留。
>
> 目前剩下的是产品契约选择，而不是仓库事实。尤其“导入是否允许合并到已有数据”和“初始化是否必须支持自动化”会显著改变冲突处理、CLI 接口和测试规模；我先把这三项锁定，再给出最终计划。
>

> # CapsLock v1.9.0 生命周期与运维治理开发计划
>
> ## 总结
>
> 以当前 v1.8.0、fresh-v2 workspace/memory schema v2 和 120 项测试为基线，补齐初始化、配置治理、凭据、备份迁移、诊断修复和发布供应链。
>
> 按已确认的取舍：
>
> - 只保证 v1.8.0 到 v1.9.0 的自动升级，不实现 roadmap 原定的 v1.3.x 全链数据库迁移；同步修订 roadmap 和迁移文档。
> - `init` 同时支持交互向导和非交互脚本。
> - 系统安全存储通过基础依赖 `keyring` 提供，不可用时引导使用环境变量引用。
> - 全量导入允许合并已有数据；冲突使用确定性 ID 重映射。
> - 导入未完成工作和审批，但绝不自动执行；历史批准必须重新确认。
>
> ## 公开接口
>
> - 新增 `capslock init [--non-interactive ...] [--update] [--check-provider]`。
>   - 单模型初始化为一个 provider/profile，并同时用于 `reasoning` 和 `fast`。
>   - 支持 provider、base URL、model、credential ref、权限模式、memory 开关和可选 Tavily 配置。
>   - 已有配置默认只验证；`--update` 在备份后做增量更新。
>   - 网络连通测试必须显式启用，执行前展示 provider 和外发行为。
>
> - 新增 `capslock config validate [--json]` 和 `capslock config migrate [--dry-run|--apply]`。
>   - TOML 根字段新增 `config_version = 1`。
>   - provider 使用 `credential = "env:NAME"` 或 `credential = "keyring:NAME"`。
>   - v1.8 无版本配置视为 v0；迁移前备份并原子替换。
>   - 未知字段、错误类型和无效引用报错；旧 `[model]` 单模型配置保留至 2.0，但显示弃用提示。
>
> - 新增 `capslock credentials status|set|delete`。
>   - `set` 使用隐藏输入或 `--stdin`，禁止通过命令参数传递密钥。
>   - keyring 后端不可用时明确失败并给出环境变量方案，不静默切换来源。
>   - 输出、异常、事件和诊断只显示 credential ID 与可用状态。
>
> - 新增 `capslock backup create|list|verify|restore`。
>   - 使用 SQLite backup API 生成 workspace 与完整 user-memory 一致性快照，并包含受管配置、MCP、事件和 Skill 文件。
>   - keyring 内容、`.env` 和 MCP 明文环境变量不进入备份；被移除的值写入缺失项报告。
>   - `restore` 先备份现状、校验 manifest/checksum/schema，再经确认原子替换。
>
> - 新增 `capslock export DEST [--include-global-memory]` 与 `capslock import ARCHIVE [--yes]`。
>   - 支持新的 `capslock-lifecycle-export` v1，以及 v1.8 session-export v2、memory-export v3。
>   - portable export 包含会话、消息、工作流、审批/action、来源、引用、任务和 workspace/session 记忆；默认不含全局记忆。
>   - 不导出模型配置、凭据、embedding 向量/同意、缓存或用户级 Skill；MCP 声明移除 env 值。
>   - archive 使用版本化 manifest、稳定 archive ID、SHA-256 和有界文件清单。
>
> - 增强 `capslock doctor [--json] [--strict] [--network] [--fix] [--yes]`。
>   - 默认只读；任何写修复都要求 `--fix` 和逐项确认，`--yes` 仅供明确的非交互调用。
>   - 正常模式遇到 error 返回 1；`--strict` 同时将 warning 视为失败；CLI 用法错误仍返回 2。
>
> ## 实现阶段
>
> 1. **配置、凭据与初始化**
>    - 将配置解析拆成“原始读取、schema 校验、迁移、解析为 Settings”四层，使配置损坏时 `doctor` 仍可运行。
>    - 使用支持保留注释的 TOML API 完成 v0→v1 迁移；普通启动可自动迁移，失败保留原文件和备份。
>    - 建立环境变量与 keyring 两种 credential provider；所有模型、Tavily 和可引用的 MCP 凭据统一通过该接口读取。
>    - `init` 先在临时文件生成并验证完整配置，再原子落盘；不会创建或修改 `.env`。
>
> 2. **数据库与生命周期操作**
>    - workspace 和 memory schema 升至 v3，增加 import batch、实体映射、源指纹、处理结果和失败恢复记录。
>    - action 增加导入来源、`historical_only` 与 `requires_reapproval` 标记；导入的已完成文件动作不能在目标工作区执行 undo。
>    - 保留现有同 application ID 的顺序迁移链；正式升级保证为 v1.8 schema v2→v3。旧 application ID 和 v1 旧布局继续拒绝并给出明确文档入口。
>    - 生命周期操作使用 workspace/user advisory lock、操作 journal 和迁移前双数据库备份；崩溃后停止普通启动，由 `doctor --fix` 确认回滚。
>
> 3. **安全合并**
>    - 导入前完成全包校验、路径穿越/符号链接/特殊文件拒绝、大小和记录数限制以及引用图检查。
>    - 同 ID 且规范化内容完全一致时跳过；同 ID 不同内容使用 archive ID、实体类型和旧 ID 生成确定性新 ID，并重写全部外键。
>    - 重复导入同一 archive 为幂等 no-op；生成 imported/skipped/remapped/blocked 的机器可读和终端报告。
>    - workspace/session memory 重新绑定目标 workspace，global memory 仅在显式选项下导入；不得造成跨工作区召回。
>    - MCP 同名同内容时跳过；冲突声明确定性改名，缺少凭据的 server 保持 disabled，并同步重写待审批 MCP action 引用。
>
> 4. **未完成工作恢复**
>    - `queued` work item 保持 queued，但导入结束后不自动进入 worker；新增 `/queue start <id>` 供用户显式启动。
>    - `running` run 转为 `interrupted`，保留稳定检查点并沿用现有 `/queue retry`。
>    - `waiting_approval` 保持可审阅；原 pending 保持 pending，approved/running action 重置为 pending。
>    - 每个导入 action 在批准时重新执行路径、命令、网络、MCP 和风险校验；批准时间和旧权限模式不能跨工作区复用。
>
> 5. **Doctor 与发布治理**
>    - 检查配置 schema/弃用、credential ref、布局与符号链接、私有文件权限、SQLite ID/version/quick-check/foreign key、迁移 journal、MCP、Skill、路由和预算。
>    - 可修复项限定为创建缺失目录、修正权限、备份后迁移配置/数据库、重建索引、恢复未完成生命周期操作和标记遗留 running 状态。
>    - 不自动安装软件、修改 Git、覆盖冲突配置、旋转凭据或进行网络调用。
>    - CI 在 Linux/macOS、Python 3.11/3.12 上生成 wheel/sdist 和 CycloneDX JSON SBOM，执行 Ruff、完整测试、固定评测、依赖审计、密钥扫描、Twine 与隔离安装冒烟。
>    - 更新 README、Agent Reference、v1.9 开发/发布说明、CHANGELOG、升级与回滚文档；版本源升至 `1.9.0`，发布资产包含 wheel、sdist、SBOM 和校验值。
>
> ## 测试与验收
>
> - 空环境通过交互和非交互 `init`，配置有效、凭据可解析，并能完成首个模型请求；取消向导不留下半成品。
> - v1.8 config v0、workspace schema v2 和 memory schema v2 可备份并升级到 v1.9；失败和进程中断后原数据可恢复。
> - keyring 正常、无后端、锁定和删除场景均有测试；密钥不出现在 argv、终端、JSON、日志、数据库、portable export 或 Git。
> - backup 可验证、篡改包被拒绝、恢复前自动备份；portable archive 的路径穿越、符号链接、超限和伪造引用全部拒绝。
> - 导入覆盖 ID 冲突重映射、跨表引用、重复导入、MCP 冲突、memory scope、全局记忆 opt-in 和跨数据库失败回滚。
> - 导入的 queued/running/waiting-approval 状态可见但不自动执行；旧批准必须重新确认，历史文件动作不能撤销目标工作区文件。
> - `doctor` 在无配置、损坏配置、错误 schema、缺失凭据和未完成 journal 下仍能输出结构化诊断；未经确认不写文件。
> - 发布前完整回归、核心评测、构建、SBOM、依赖审计和 wheel 安装冒烟全部通过。
>
> ## 假设与边界
>
> - v1.8.0 的 CI、tag 和 Release 应先完成，再建立 v1.9 发布基线。
> - 不支持 v1.3.x–v1.7.x 数据库直接迁移；该项从 v1.9 roadmap 中移除，不暗示已实现。
> - portable import 是数据合并，不替换目标模型配置或复制凭据；精确回滚使用 `backup restore`。
> - 支持平台保持 Linux、macOS 和 Python 3.11/3.12；不新增云同步、账户、插件市场或系统软件自动安装。
