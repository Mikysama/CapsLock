>
> 路线图已经明确 v1.7.0 的核心不是增加 Agent 权限，而是把现有同步 CLI 升级为可管理的工作流界面。接下来我会补齐该版本的非目标、现有运行时事件/任务/审批数据模型，以及当前 UI 技术栈，避免计划停留在“做一个 TUI”的抽象层面。
>
> 目前的关键技术约束也确认了：模型接口、工具循环、命令/Web/MCP 执行都是同步阻塞式；现有 `TaskInfo` 只是任务清单，还不是可恢复的执行计划。因此 v1.7.0 若要真正满足取消、重试和稳定点恢复，必须先补事件流与前台运行状态机，而不能只在 Rich 输出外包一层全屏界面。
>
> 有三个产品决策会显著改变 v1.7.0 的兼容策略与存储设计，我需要先锁定：TUI 是否成为默认入口、恢复的精度，以及会话导出的交付形态。仓库本身无法替你决定这些偏好。
>
> 我把你的回答理解为：像 Codex/Claude Code 一样，裸命令进入交互式终端应用；诊断、会话管理、迁移等仍是普通 CLI 子命令；脚本调用走独立的非交互入口。还需要锁定一个细节：两者的终端呈现并不完全相同，Claude Code 更偏保留 scrollback 的行内 UI，Codex 更偏应用式 TUI，这会影响布局和测试方案。
>
> 你选择的是“参考两者”而不是照搬某一种，我会落成一个明确的混合方案：默认是保留 scrollback 的行内聊天体验，计划与运行状态常驻可见；审批中心、会话管理和详情使用键盘可打开的覆盖面板，避免宽窄终端维护两套应用。由于这里涉及 Codex 的现行 CLI 交互约定，我会用 `openai-docs` 技能核对官方信息，只借鉴入口和交互模式，不把 CapsLock 绑定到 OpenAI API。

> # CapsLock v1.7.0 工作流 TUI 开发计划
>
> ## 总结
>
> 基于当前 v1.6.0、workspace schema v5 和 145 项测试，将同步 CLI 演进为 Codex/Claude Code 风格的终端工作流应用：裸 `capslock` 在 TTY 中启动行内 TUI，保留终端 scrollback；计划、运行状态常驻，审批、会话和详情通过覆盖面板管理。
>
> 本版本不扩大文件、命令、Web、MCP 或记忆权限，不引入后台进程。重点是异步事件流、可取消运行、工具轮次检查点、集中审批和完整会话治理。
>
> ## 六周里程碑
>
> 1. **第 1 周：运行契约与 schema v6**
>    - 定义运行事件、工作项、步骤检查点、取消令牌和恢复协议。
>    - workspace schema v5 自动备份并迁移到 v6；失败事务回滚。
>    - 增加工作项队列、run 父子关系、步骤、事件、会话归档和搜索索引。
>    - 为任务增加 `run_id` 和顺序，使计划视图能区分不同用户请求。
>
> 2. **第 2 周：流式与可取消异步内核**
>    - 增加异步模型流接口，组装文本增量、工具调用参数和最终 usage。
>    - 将命令、Web、MCP 长操作改为可取消异步执行；SQLite 短事务仍由主事件循环串行访问。
>    - 统一发出 `queued/thinking/tool_running/waiting_approval/completed/failed/cancelled` 事件。
>    - “thinking”只展示状态，不输出模型隐藏推理过程。
>
> 3. **第 3 周：检查点、重试与审批中心**
>    - 每个完整模型响应及其全部工具调用提交后生成稳定检查点；部分流式输出不作为恢复点。
>    - 重试创建关联的新 run，从最近稳定检查点恢复，不重新执行已成功工具或副作用动作。
>    - 中断且结果不确定的命令/MCP 动作标为 cancelled，重试必须生成新动作并重新审批。
>    - 文件、命令、Web、MCP 提案统一进入审批队列，持久化风险、脱敏载荷、回滚说明、决定与结果。
>    - 同一轮多个审批全部得到决定后才自动续跑；取消 run 时未决定动作统一取消。
>
> 4. **第 4 周：行内工作流 TUI**
>    - 使用现有 `prompt-toolkit` 构建异步行内应用，Rich 继续承担经典和非交互渲染，不引入第二套 TUI 框架。
>    - 主界面包含对话流、输入区、计划、前台队列和模型/权限/token 状态栏。
>    - 覆盖面板提供审批中心、来源与引用、上下文构成、记忆命中、费用和会话管理。
>    - 80 列使用单列折叠布局，120/160 列逐步展开；所有状态同时使用文字标识，兼容 `NO_COLOR`。
>    - `Ctrl-C` 第一次取消当前运行，空闲时再次退出；`Esc` 关闭面板，Tab/方向键/Enter 完成导航。
>
> 5. **第 5 周：会话治理与脚本入口**
>    - 当前工作区内支持标题和消息全文搜索、归档/恢复归档、重命名、导出和永久删除。
>    - 删除采用两阶段流程：标记 deleting、清理 session 级记忆与候选、级联删除工作区记录；中断后可继续完成。
>    - 导出原子生成 `<destination>/session.json` 和 `session.md`，覆盖对话、引用、来源、文件 diff、命令输出、外部动作、审批和费用。
>    - 导出默认脱敏密钥和敏感载荷，不包含系统提示、原始检查点或其他作用域记忆正文。
>    - 新增 `capslock exec [PROMPT] [--json]`；无参数时从 stdin 读取。`--json` 输出版本化 JSONL 事件。
>    - 保留 `capslock ask` 作为兼容别名；非交互环境不弹审批，遇到待审批动作输出事件并以退出码 3 结束。
>
> 6. **第 6 周：兼容、压力测试与发布**
>    - 补齐 PTY、进程组、迁移、恢复、窄终端和 JSONL 契约测试。
>    - 更新 README、agent reference、v1.7 开发文档、CHANGELOG、发布说明和降级步骤。
>    - 更新唯一版本源为 `1.7.0`，完成构建、wheel 隔离安装、发布校验和 `v1.7.0` tag。
>
> ## 公开接口与数据契约
>
> - 裸 `capslock`、`capslock chat`：TTY 默认进入 TUI；`--classic` 保留现有交互模式，至少兼容到 v1.8.0。
> - `capslock exec`：稳定脚本入口；纯文本只写最终回答，`--json` 输出带 `schema_version`、序号、时间、session/run/work-item ID、事件类型和脱敏 payload 的 JSONL。
> - `capslock sessions search|archive|unarchive|export|delete`：为 TUI 会话操作提供等价的可测试 CLI。
> - 新增 `WorkspaceAgent.ask_stream(...) -> AsyncIterator[AgentEvent]`；现有 `ask()` 消费事件并返回 `WorkspaceAnswer`，保持调用方兼容。
> - `ChatModel` 增加流式适配协议；不支持流式的测试或第三方模型退化为单个最终增量。
> - schema v6 增加 `work_items`、`run_steps`、`run_events`、会话 FTS，并扩展 runs/actions/tasks；用户记忆 schema 保持 v2。
>
> ## 验收与测试
>
> - 流式文本、碎片化工具参数、usage 缺失和传输失败均产生顺序稳定、可重放的事件。
> - 在模型、命令、Web、MCP 和等待审批阶段按 Ctrl-C，run 与动作状态明确，已启动子进程组在宽限期后被终止。
> - 从任意稳定检查点恢复不会重复已完成文件写入、命令或 MCP 调用；部分输出被丢弃并从上一检查点重新生成。
> - 队列支持新增、取消、重排和失败重试；进程退出后不继续执行，遗留队列下次启动只展示、不自动运行。
> - 会话搜索覆盖中英文标题和消息；归档默认隐藏；删除无跨库孤儿；导出包可脱离数据库独立审阅。
> - 使用 PTY 快照验证 80/120/160 列、CJK、`TERM=dumb`、`NO_COLOR`、键盘导航和无内容重叠。
> - 完整通过 Python 3.11/3.12、Linux/macOS 的 pytest、Ruff、pip check/audit、仓库检查、build、Twine 和 wheel 冒烟。
>
> ## 假设与边界
>
> - 排期按 2 名工程师、6 周估算；运行时/存储与 TUI/会话管理在契约完成后并行。
> - “参考 Codex 和 Claude Code”指默认交互入口、行内对话、持续状态和独立脚本入口，不复制其内部实现。
> - 会话管理限定当前工作区，不增加跨工作区索引。
> - 不展示隐藏思维链，不增加远程控制、daemon、定时任务、后台续跑或新权限能力。

> 什么是tui，和cli有什么区别

CLI（Command-Line Interface）是“命令行接口”的总称。用户输入一条命令，程序执行并输出结果，例如：

```bash
capslock exec "检查测试状态"
capslock sessions search "发布计划"
```

TUI（Terminal User Interface）是运行在终端里的交互式界面，通常包含持续刷新的状态区、菜单、列表、键盘导航和输入框。它仍然属于 CLI 应用的一种交互形态，但更像终端中的桌面应用。

可以简单理解为：

| CLI | TUI |
|---|---|
| 一条命令对应一次操作 | 在持续运行的界面中操作 |
| 适合脚本、CI 和自动化 | 适合人工交互和长任务 |
| 输出通常从上到下打印 | 状态、队列和菜单可以动态更新 |
| 参数决定行为 | 键盘导航、面板和快捷命令决定行为 |
| 例如 `capslock exec` | 例如直接运行 `capslock` |

在 CapsLock v1.7.0 中：

- `capslock exec "问题"` 是非交互 CLI，执行完就退出。
- `capslock sessions ...` 是会话管理 CLI。
- 直接运行 `capslock` 会进入 TUI，可以持续对话、查看计划和队列、处理审批。
- `capslock chat --classic` 使用旧式的逐行交互 CLI。

所以两者并不互斥：CapsLock 整体是 CLI 程序，而 TUI 是它面向人工操作的交互界面。

当前代码里的 `6` 不是“最多调用 6 个 function”，而是“最多进行 6 轮包含工具调用的模型交互”。

具体流程是：

1. 模型返回一个或多个工具调用，算作 1 轮。
2. CapsLock 顺序执行这一轮的所有工具。
3. 工具结果返回模型，进入下一轮。
4. 最多执行 6 个工具轮次。
5. 第 6 轮完成后，额外允许第 7 次模型请求生成最终答案，但这次不能再调用工具；否则报 `agent exceeded the maximum number of tool-call rounds`。

因此，一轮如果同时包含 `read_file`、`search_files`、`list_files` 三个调用，实际执行了 3 个 function，但只消耗 1 个 `max_turns`。实现位于 [runtime_support.py](./capslock/runtime_support.py:161)，对应边界测试在 [test_workflow_v17.py](./tests/test_workflow_v17.py:277)。

`6` 只是默认值，不是代码硬上限，可以通过以下方式调整：

```bash
export CAPSLOCK_MAX_TURNS=10
```

或者 `.capslock/config.toml`：

```toml
[model]
max_turns = 10
```

默认值定义在 [config.py](./capslock/config.py:102)。

代码库中没有记录“为什么精确选择 6”的基准测试或设计论证。它本质上是一个保守的防失控阈值，用于限制模型反复搜索、读取失败重试造成的无限循环、token 消耗和延迟。对于代码库总结这类任务，6 轮确实偏紧，建议设为 `10` 到 `12`。

从接口设计上看，`max_turns` 这个名字不够准确，更合理的是拆成：

- `max_tool_rounds`：模型与工具往返轮数。
- `max_tool_calls`：实际 function 执行总数。
- `max_run_seconds`：总运行时间。
- token 或费用预算。

目前 CapsLock 只有第一项，所以“最多 6 次 function calling”这个理解并不准确。

参考 Anthropic 官方文档后，结论很明确：Claude Code 不使用固定的“6 轮”作为交互式会话上限。

| 场景 | Claude Code 行为 |
|---|---|
| 交互式 `claude` | 没有公开的固定 turn 上限，持续执行直到任务完成、用户中断、权限阻塞或服务限制 |
| 非交互 `claude -p` | 支持可选 `--max-turns`，默认不限制 |
| Agent SDK | `max_turns=None` / `maxTurns=undefined`，默认不限制 |
| 成本控制 | 单独提供 `--max-budget-usd` / `max_budget_usd` |
| 达到限制 | 返回明确的 `error_max_turns` 或 `error_max_budget_usd` 结果 |

官方资料：

- [Claude Code CLI reference](https://code.claude.com/docs/en/cli-reference#cli-flags)
- [Claude Agent SDK Python reference](https://code.claude.com/docs/en/agent-sdk/python#claudeagentoptions)
- [Claude Code headless mode](https://code.claude.com/docs/en/headless)

Claude Code 的设计重点不是用一个很小的轮次数字兜底，而是组合这些机制：

- 用户可随时按 Escape 中断。
- 每个危险工具调用经过权限系统。
- 上下文过长时压缩，而不是因 turn 数退出。
- 脚本模式可显式设置轮数和美元预算。
- SDK 返回结构化停止原因。
- 长任务可以拆给子 Agent，每个子 Agent拥有独立的 `maxTurns`。
- 文件操作支持 checkpoint/rewind。

对 CapsLock，我不建议简单地从 `6` 改成“完全无限”。CapsLock 当前没有 `max_budget_usd`、重复调用检测和总运行时间预算，直接取消限制可能造成模型持续读取文件或重复调用工具。

更合适的方案是：

1. 交互式 TUI 默认改为软限制 `32` 轮。
2. 达到软限制时暂停，并允许用户选择“继续 16 轮”或“停止并总结”，而不是直接失败。
3. `capslock exec` 保留硬限制，默认 `32` 轮，并支持 `--max-turns`。
4. 增加独立的总工具调用数限制，例如 `128` 次。
5. 相同工具和相同参数连续出现 3 次时判定为循环。
6. 增加总运行时间、token 和费用预算。
7. 将容易误解的 `max_turns` 重命名为 `max_tool_rounds`。
8. 达到任何限制时生成结构化停止原因，例如 `max_tool_rounds`、`max_tool_calls`、`max_duration`、`repeated_call`。

短期最务实的修改是将默认值由 `6` 提高到 `32`；长期则应采用 Claude Code 风格的“交互式软限制 + 脚本硬预算 + 循环检测”，而不是依赖单一轮次阈值。
