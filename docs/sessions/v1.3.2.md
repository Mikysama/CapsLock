当前代码可以继续运行，`.venv/bin/pytest -q` 为 `56 passed`，ruff 也通过。真正需要优先处理的不是格式或小函数，而是应用层职责缺失，导致 CLI、工具适配器和领域服务互相承担业务编排。

建议的目标依赖方向是：

```text
CLI / 模型工具
      ↓
应用层 ActionCoordinator
      ↓
Change / Command / Web / MCP 领域服务
      ↓
Repository / HTTP / subprocess / MCP adapters
```

**1. 优先抽离 CLI 中的业务编排**

[cli.py](./capslock/cli.py:442) 同时负责：

- prompt-toolkit 输入和 Rich 渲染
- 斜杠命令解析与路由
- 依赖和服务实例化
- 文件、命令、Web、MCP 的审批与执行
- ID 前缀解析
- Web 完成后的 Agent 自动续答

尤其是审批执行逻辑从 [cli.py:609](./capslock/cli.py:609) 一直延伸到 MCP/Web 编排。它们不是 UI 逻辑，未来增加 TUI、JSON 输出或非交互模式时会被迫复制。

建议拆成：

- `cli/app.py`：启动和依赖装配
- `cli/chat.py`：输入循环与命令路由
- `cli/prompt.py`：补全、lexer、键位
- `cli/render.py`：Rich 输出
- `application/actions.py`：统一审批、拒绝、执行和查询

同时让 `COMMAND_TREE` 中的命令声明直接关联 handler，消除 [命令目录](./capslock/cli.py:107) 与 [大型 if 链](./capslock/cli.py:455) 的双重维护。

**2. 建立统一但有限的动作生命周期**

文件变更、命令和外部动作分别实现了相似状态流：

- [ChangeService](./capslock/changes.py:57)
- [CommandService](./capslock/execution.py:80)
- [ExternalActionService](./capslock/external.py:20)

目前存在 `discarded`、`rejected` 等不一致状态，状态转换也依赖散落的字符串判断。建议增加：

- `ActionStatus` 枚举
- 合法状态转换表
- `ApprovalCoordinator`
- 统一的 ID 前缀解析和会话归属验证

不要把三个执行器强行合成一个基类。文件写入、子进程和外部调用的安全约束不同，只共享状态机和审批策略即可。

**3. 拆分 SessionStore**

[session.py](./capslock/session.py:92) 同时包含领域模型、建表、迁移以及所有实体的 CRUD。随着 v1.4 记忆功能进入，这个文件会迅速成为瓶颈。

建议拆为：

- `domain/models.py`
- `storage/database.py`
- `storage/migrations.py`
- `storage/sessions.py`
- `storage/actions.py`
- `storage/sources.py`

还应补上显式事务、连接关闭/context manager 和版本化 schema。现在多数方法单独 `commit()`，审批与执行之间无法形成明确事务边界，建表逻辑也只有一次 `_ensure_column` 式迁移。

**4. 收敛配置和服务构造**

配置参数目前经过三层逐项搬运：

- [Settings](./capslock/config.py:11)
- [WorkspaceAgent 构造函数](./capslock/runtime.py:47)
- [RunContext](./capslock/tools.py:38)

然后 CLI 和 tools 又分别构造 `ChangeService`、`CommandService`、`WebService`、`McpService`。建议引入分组配置：

```python
RuntimeConfig
CommandConfig
WebConfig
McpConfig
```

再由一个 `ServiceFactory` 或 `WorkspaceServices` 负责创建服务。`RunContext` 只保留运行身份、策略、服务集合和权限模式，避免目前十多个位置参数的脆弱调用。

**5. 拆分 tools.py，并统一权限元数据**

[tools.py](./capslock/tools.py:71) 混合了注册表、文件搜索、Git、任务、动作适配和全部 JSON Schema。

更重要的是，`Tool` 自己有 `risk_level`、`requires_approval`，而真正的风险判断又由 [permissions.py](./capslock/permissions.py:33) 根据工具名重新计算。两个来源将来很容易不一致。

建议拆成：

- `tools/core.py`
- `tools/workspace.py`
- `tools/git.py`
- `tools/tasks.py`
- `tools/actions.py`
- `tools/catalog.py`

并让风险、审批需求和回滚说明只有一个权威来源。

**6. 解耦模型运行时**

[WorkspaceAgent.ask](./capslock/runtime.py:89) 同时处理模型 API、工具循环、上下文压缩、引用解析、运行持久化、费用和事件。

建议先抽出一个很小的 `ChatModel` Protocol，将 OpenAI SDK 响应转换为内部消息模型。随后再分离：

- `ContextBuilder`
- `ToolLoop`
- `CitationResolver`
- `RunRecorder`

这会直接为路线图中的多模型路由铺路，也能避免测试持续使用深层 `SimpleNamespace` 模拟 OpenAI 对象。

**7. 拆开 Web 领域与通用外部动作**

[external.py](./capslock/external.py:20) 同时包含通用动作状态、SSRF 校验、HTML 解析、Tavily 客户端和来源持久化。至少应将 `ExternalActionService` 移到独立模块，使 Web 和 MCP 都依赖它，而不是让 MCP 依赖名为 `external.py` 的 Web 模块。

另外，Web 的 `httpx.Client` 没有明确关闭，MCP 使用 `asyncio.run()`，未来切换异步 TUI 时也会形成阻碍。

**8. 统一脱敏和文件类型策略**

当前有两套不同的脱敏逻辑：

- CLI 递归按 key 脱敏：[cli.py:903](./capslock/cli.py:903)
- 事件日志正则脱敏：[observability.py:12](./capslock/observability.py:12)

`TEXT_SUFFIXES` 也在 [policy.py](./capslock/policy.py:9) 和 [tools.py](./capslock/tools.py:23) 重复。两者都属于安全边界，应各自只有一个来源。

综合排序：v1.3.2 最适合先做“CLI 拆分 + ActionCoordinator + 配置/服务工厂”，这三项收益最高且不要求改变 SQLite 格式；`SessionStore` 的迁移框架可以作为 v1.4 记忆功能前置工作。当前仅完成审查，没有修改代码。

> # CapsLock v1.3.2 代码库解耦方案
>
> ## 总结
>
> 进行完整但保持同步调用模型的架构重构：引入统一动作主表与应用协调层，拆分存储、CLI 和模型运行时，并统一安全策略、状态和资源生命周期。保持现有 CLI 参数、配置项和主要用户工作流兼容；允许整理状态名称、错误信息和内部 Python 接口。
>
> 实施采用分阶段提交，每阶段均需通过完整测试后再进入下一阶段。
>
> ## 核心改造
>
> ### 1. 统一领域类型与配置
>
> - 新建独立领域模型，定义 `ActionType`、`ActionStatus`、`ActionResultKind`、`ActionInfo`，避免领域对象继续依赖 `session.py`。
> - `ActionStatus` 固定为 `pending/approved/running/completed/failed/rejected/cancelled`。
> - `ActionResultKind` 保存领域结果，例如 `applied`、`undone`、`exit_zero`、`nonzero_exit`、`timeout`、`execution_error`、`success`。
> - 将扁平 `Settings` 分组为模型、命令、Web、MCP 和运行时配置；外部环境变量与 TOML 名称保持不变。
> - `RunContext` 改为关键字构造，只保留运行身份、工作区策略、动作协调器、权限和事件接口。
> - 集中维护文本文件类型、安全脱敏和风险定义，删除 `TEXT_SUFFIXES`、CLI 脱敏和事件脱敏的重复实现。
>
> ### 2. 重构数据库和 Repository
>
> - 引入 `PRAGMA user_version` 驱动的顺序迁移器，新 schema 版本设为 `1`。
> - 新建统一 `actions` 主表，保存 ID、session/run、动作类型、通用状态、结果类型、摘要、各阶段时间和错误。
> - 建立 `file_action_data`、`command_action_data`、`external_action_data` 领域明细表；sources、sessions、messages、runs、tasks 和 settings 保持原有数据结构。
> - 将 `SessionStore` 拆为数据库连接管理、迁移器以及 session、run、action、source、task repositories。
> - Repository 提供事务、上下文管理和显式 `close()`；本次不新增外键约束，以保证历史库中可能存在的孤立审计记录仍可升级。
> - 所有会话归属检查、ID 前缀匹配和状态查询由 `ActionRepository` 统一处理。
>
> 迁移规则：
>
> - `changes.applied → completed/applied`
> - `changes.undone → completed/undone`
> - `changes.discarded → rejected/null`
> - `commands.completed → completed/exit_zero`
> - 命令失败根据 error 和 exit code 映射为 `timeout`、`nonzero_exit` 或 `execution_error`
> - 外部动作完成映射为 `completed/success`，失败映射为 `failed/execution_error`
> - 迁移前使用 SQLite backup API 在 `.capslock/backups/` 创建带旧 schema 版本和时间戳的备份。
> - 在单个事务中重命名旧表、创建新表、复制数据、校验记录数和 ID 唯一性后删除旧表。
> - 发现跨旧表重复 action ID、数据校验失败或迁移异常时回滚事务、保留备份并阻止应用启动。
>
> ### 3. 引入应用层动作协调器
>
> - 新建 `ActionCoordinator`，作为 CLI 和模型工具执行动作的唯一入口。
> - 对外提供 `propose`、`approve_and_execute`、`reject`、`execute_auto_approved`、`reverse_last_file_action` 和查询接口。
> - 统一执行状态流：`pending → approved → running → completed/failed/cancelled`，拒绝走 `pending → rejected`。
> - 文件撤销保持 `status=completed`，将 `result_kind` 从 `applied` 更新为 `undone` 并记录 `reversed_at`。
> - 风险等级、审批要求、回滚说明和自动审批事件由 `ApprovalPolicy` 统一决定。
> - 文件、命令、Web 和 MCP 保持独立 handler，只共享动作生命周期，不创建包办所有执行细节的通用基类。
> - Web/MCP 的重复开始、成功、失败和事件记录移入协调器。
> - HTTP client、数据库连接和其他资源由应用容器统一创建和关闭。
>
> ### 4. 拆分工具与模型运行时
>
> - 将工具系统拆为注册表核心、工作区/Git 工具、任务工具和动作工具目录。
> - `Tool` 不再保存独立的风险与审批字段；工具只声明名称、schema 和 handler，策略由动作类型决定。
> - 引入同步 `ChatModel` Protocol 和内部 `ModelRequest/ModelResponse/ToolCall/Usage` 类型。
> - OpenAI 兼容 SDK 封装为 adapter；`WorkspaceAgent` 不再读取 SDK 私有对象结构。
> - 将 `WorkspaceAgent.ask` 拆为上下文构建、工具循环、引用解析和运行记录组件。
> - EventSink 增加按运行截取事件的能力，回答只返回当前 run 的事件，不再累积以前运行的事件。
> - MCP SDK 的 async 调用封装在同步 adapter 内；本次不异步化 CLI 或 Agent 公共接口。
>
> ### 5. 拆分 CLI
>
> - composition root 只负责解析参数、加载配置和创建 `WorkspaceApplication`。
> - chat 模块只管理输入循环；prompt 模块负责补全、lexer 和按键；render 模块负责 Rich 输出。
> - 用声明式 `CommandSpec` 同时生成命令目录、补全和路由，消除 `COMMAND_TREE` 与 if/elif 分发的双重维护。
> - 审批、拒绝、执行、撤销和 Web 自动续答调用 `ActionCoordinator`，CLI 不再直接实例化领域服务或修改状态。
> - 保持现有 CLI 参数和斜杠命令；列表中的状态统一显示新状态，并可附加 `result_kind`。
> - 私有 `_approve_*`、`_resolve_*` 等函数不提供兼容转发层，相应测试迁移到新应用层接口。
>
