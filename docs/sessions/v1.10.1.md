# 检查可解耦重构模块

> 再次检查capslock核心代码库，有哪些模块是可以解耦重构的？

<details><summary>4 previous messages</summary>

> 我会按“依赖方向、职责混杂、全局状态/副作用、可测试性”重新梳理核心代码；先定位仓库约束与模块边界，再给出按收益和风险排序的解耦建议，并引用具体文件位置。
>
> 当前代码已经是 v2 分层架构，之前的“大模块拆包”多数已完成；这次更值得关注的是分层内部仍存在的“隐性组合根”和重复策略，而不是继续按文件行数机械拆分。我正在核对几处大文件的调用方向与事务边界。
>
> 目前已确认两类高价值耦合：一是 `WorkspaceApplication.open()` 通过 `agent_ref` 让动作工厂反向读取尚在构造中的 Agent；二是工具层的 `RunContext` 直接携带完整 repository bundle、动作协调器、策略、记忆和 Skill，实际上成了 service locator。下一步会结合现有边界测试判断哪些拆分能保持事务安全。
>
> 完整测试仍在运行，目前已超过一半且没有失败。测试本身也暴露了构造环：运行时测试必须复制 `agent_ref["agent"]` 的回填方式才能注入审批回调，这说明它不是单纯的实现细节，而是已经外溢到测试装配层。
</details>

结论：v2 的大分层已经成形，不需要再次全面推倒重来。当前最值得重构的是 5 个核心边界，其中“应用—运行时—工具”的循环依赖应优先处理。

## 优先级建议

| 优先级 | 模块 | 主要问题 | 建议目标 |
|---|---|---|---|
| P0 | `application / runtime / tooling` | 包级循环依赖、service locator、构造回填 | 引入窄接口与独立 composition root |
| P0 | `runtime.agent / model routing / tool loop` | 隐式模型能力、单函数编排过重 | 显式 Model Session、RunJournal、步骤执行器 |
| P1 | `lifecycle.py` | 备份、归档、导入、SQLite 合并集中在 1150 行 | Archive、Backup、ImportCoordinator 分离 |
| P1 | memory service/repository | 生命周期、检索、来源、设置、审计混在同一 repository | 按聚合拆 repository，保留 facade |
| P1 | workflow repository | 领域状态规则落在 SQLite repository | 纯领域状态机 + 原子事务写入器 |
| P2 | config / database migration | 读取带迁移副作用，通用数据库类硬编码版本特例 | Config pipeline、MigrationStep |
| P3 | CLI / Web-MCP handlers | 命令和展示边界仍偏宽 | 功能增长时再拆 |

### 1. 先消除应用、运行时和工具之间的循环依赖

当前依赖方向实际是：

```text
application -> runtime -> tooling -> application
                       `-> storage
```

证据包括：

- [application/app.py](./capslock/application/app.py:133) 用 `agent_ref` 回填尚未构造完成的 Agent，动作工厂再反向读取 Agent 的权限和审批回调。
- [runtime/agent.py](./capslock/runtime/agent.py:15) 直接依赖应用层 `ActionCoordinator` 和 `WorkflowService`。
- [tooling/async_core.py](./capslock/tooling/async_core.py:11) 又依赖应用层动作协调器和完整 repository bundle。
- [tests/test_runtime_v2.py](./tests/test_runtime_v2.py:108) 测试也必须复制 `agent_ref["agent"]` 装配方式，说明耦合已经外溢。

建议：

- 将 `WorkspaceApplication` 移到独立 `bootstrap.py` 或 `composition.py`，允许它依赖所有具体实现。
- 在 `application/ports.py` 定义 `WorkflowPort`、`ActionPort`、`RunJournal`、`TaskPort`、`SourcePort`、`MemoryPort`、`SkillPort`。
- 将 `RunContext.repositories` 替换成所需的窄接口；工具不应取得完整 repository bundle。
- 将权限模式和审批回调封装成显式 `RunInteraction`，直接传给动作协调器，删除 `agent_ref`。

这是目前收益最大的重构。

### 2. 拆解运行时编排，并显式化模型能力

[WorkspaceAgent._execute()](./capslock/runtime/agent.py:186) 同时负责：

- workflow 准备和结束；
- Skill 解析；
-上下文构建；
- 模型绑定；
- 事件持久化和发布；
- ToolLoop；
- 引用处理；
- 记忆提取；
- usage/cost 汇总；
- 多类异常终止。

同时模型协议只声明了 `complete()`：[model.py](./capslock/runtime/model.py:47)，流式能力通过 `getattr` 探测；Agent 对 `bind_run`、`use_role`、`summary` 也采用相同方式。例如 [agent.py](./capslock/runtime/agent.py:217)。这使路由模型的真实契约没有被类型系统表达。

建议拆成：

- `RunOrchestrator`：准备、终止、异常收敛；
- `RunEventPublisher`：持久化、脱敏、发布事件；
- `ModelStepExecutor`：处理流式 delta；
- `ToolCallExecutor`：参数解析、调用、审计和 checkpoint；
- `RunModelSession`：显式包含 run ID、role、limits、usage summary。

[ModelRouter.complete()](./capslock/runtime/routing.py:104) 和 `stream_complete()` 的候选选择、审计、预算、重试代码也高度重复，适合共享一个 attempt driver，只让响应消费方式不同。

### 3. 拆分生命周期模块，但保留统一恢复协调器

[lifecycle.py](./capslock/lifecycle.py:113) 的 `LifecycleService` 同时管理：

- 本机备份与恢复；
- portable export/import；
- ZIP 安全与校验；
- 密钥脱敏；
- 两套 SQLite 的合并；
- ID 重映射与外键改写；
- 旧格式导入；
- journal、锁和回滚。

建议结构：

```text
lifecycle/
  archive.py          # ZIP、manifest、校验、大小限制
  backup.py           # snapshot、restore
  portable_export.py
  import_specs.py     # 表、主键、引用关系的声明
  importer.py         # 单库导入算法
  coordinator.py      # 锁、journal、双库恢复
  sanitization.py
```

注意：双数据库锁、journal 和恢复备份仍应由一个 `ImportCoordinator` 持有，不能为了拆文件破坏当前恢复语义。

### 4. 收紧 memory 的 repository 与服务边界

[MemoryRepository](./capslock/storage/memory_v2/lifecycle.py:29) 不只处理记忆 revision，还包含：

- FTS 搜索；
- access/excluded run；
- source 有效性；
- workspace settings；
- audit。

而 [semantic.py](./capslock/storage/memory_v2/semantic.py:10) 直接导入 `lifecycle.py` 的私有 `_memory`、`_visible_where`，是明确的内部耦合。

建议拆为：

- `MemoryLifecycleRepository`
- `MemoryQueryRepository`
- `MemorySourceRepository`
- `MemorySettingsRepository`
- `MemoryAuditRepository`
- `memory/query_mapping.py`：共享可见范围和 row mapper

[MemoryService](./capslock/memory/service.py:56) 可以继续作为稳定 facade，但 embedding consent/configuration 最好独立成 `EmbeddingPolicyService`；候选、召回和迁移继续委托现有子服务。

### 5. 将 workflow 状态规则从 SQLite 中抽出来

领域层目前主要是 enum 和 dataclass：[domain/workflow.py](./capslock/domain/workflow.py:10)。真正的状态转换矩阵和审批结算规则位于 [workflow repository](./capslock/storage/repositories_v2/workflow.py:77)。

建议：

- 新增纯函数 `validate_work_item_transition()`、`terminal_outcome()`、`approval_outcome()`；
- repository 继续负责 CAS 和同一事务内更新 run、work item、step、action、event；
- 不要简单把 `finalize()` 拆成多个 repository 调用，否则会破坏现有原子性。

这样领域规则可以不启动 SQLite 就进行完整矩阵测试。

## 后续可做但不紧急

- [config.py](./capslock/config.py:127)：`Settings.load()` 同时读取、自动迁移、解析环境变量和解析凭据。可拆为 `DocumentReader → Validator → Migrator → SettingsResolver`。
- [async_database.py](./capslock/storage/async_database.py:101)：通用迁移器包含 `current == 2 and label == "workspace"` 等版本特例，适合改为带 pre/post hook 的 `MigrationStep`。
- [cli/app.py](./capslock/cli/app.py:51)：parser、命令分发和 session 资源管理仍可分离，但不是核心风险。
- [cli/diagnostics.py](./capslock/cli/diagnostics.py:166)：doctor 探针、修复计划和交互确认可以分开。
- Web 与 MCP handler 当前共处 [external.py](./capslock/application/action_system/external.py:27)，依赖完全不同，后续可物理拆文件。

## 推荐实施顺序

1. 增加 ports 和独立 composition root，删除 `agent_ref`。
2. 显式化模型运行契约，给 ToolLoop 注入 `RunJournal`。
3. 提取纯 workflow 状态机。
4. 拆 lifecycle，保持归档格式和恢复语义不变。
5. 拆 memory repository/settings。
6. 最后整理 config、migration 和 CLI。

本轮只读检查，未修改代码。当前基线为：

- `150 passed`
- Ruff 检查及格式检查通过
- repository hygiene 检查通过

因此这些建议属于行为保持型架构优化，不是为了解决现有测试失败。
