# Agent 通信与可靠投递

本文说明本地 Agent 通信的运行时契约。消息保存在工作区 SQLite 的 `agent_mailbox` 中；内存通知只告诉接收运行时“数据发生变化”，不保存正文，也不承担可靠存储。

## 哪些 Agent 会处理来信

活跃父、子运行都由运行时自动收信，不要求模型记得调用读取工具。运行开始或恢复时补查数据库；之后根据接收地址的通知版本及积压状态读取。无消息变化时不在每个模型轮次查询信箱；活跃接收端每 30 秒进行一次只读兜底检查，覆盖数据库提交成功但通知丢失的情况。

问题、回复、指令能唤醒协作等待，进展与产物通知在下一安全边界合批投递。协作等待同时关注任务结束、来信、取消和截止时间，不靠反复调用模型轮询。普通消息不会中断正在生成的模型响应或执行中的工具，也不会越过审批暂停。

普通来信不会启动已结束的父 run、空闲 worker 或新任务。消息先排队，客户端显示待处理数量；必须显式 follow-up 或恢复后才激活处理。收到通知、可靠接收、投递到上下文、模型完成请求是四个不同的阶段。

## 寻址、批量与上下文

父端地址为 `session:<session_id>`，持久子端为 `worker:<worker_id>`，没有 worker 的任务为 `task:<task_id>`。旧 `sender` / `recipient` 字段继续表示父子方向；task、parent run、attempt 关联用于归属和恢复校验。身份由运行时绑定，模型不能用正文改变身份或扩展权限。`reply_to_message_id` 关联问题和回复，并校验双方地址。

父端统一使用 `send_agent_message(target_type, target_id, payload, ...)`；给任务回复时指定 `target_type="task"`、`kind="response"` 和 `reply_to_message_id`。旧 `task_id` 参数形式已移除，旧未完成调用不能按原参数继续执行，应使用新接口重新发起。子端通过绑定任务身份的 `send_parent_message` 携带 `reply_to_message_id` 回复，不由模型指定父端地址。

每次最多读取 32 封、64 KiB 正文，单封上限保持 32,000 UTF-8 字节。需要处理的消息优先；存在普通通知时，优先消息最多占 24 个名额，剩余配额供通知使用。各组按创建时间和消息 ID 稳定排序；`has_more` 表示还有积压。读取使用收件地址和待处理消息的部分索引，不加载已确认历史。空查询不写库；ACK 按批次提交。

投递还受当前上下文预算限制，放不下的正文保留待处理，不静默截断。消息只能在完整工具轮结束后、下一模型请求之前或最终完成检查时加入上下文；不会插入尚未配对的工具调用和结果之间。模型收到带消息身份及回复关联的不可信数据，不获得新的用户授权。原 run 的时间、轮数、token 与费用预算继续适用。

## ACK 与崩溃恢复

子上下文数据库可能与源信箱数据库不同，因此投递不依赖跨库事务：

1. 从源信箱有界读取并验证正文摘要。
2. 在接收端数据库保存消息信封与唯一 `(recipient_session_id, message_id)` 接收记录。
3. 接收事务提交后，再 ACK 源信箱。
4. 将消息加入模型上下文时，同一事务保存 checkpoint 和已投递标记，提交后才能请求模型。

`acknowledged` 仅表示接收运行时已可靠持有消息，**不表示模型已经理解、回复或完成工作**。问题是否得到答复由关联回复和任务状态表达。

源 ACK 前崩溃可重新读取；接收端唯一键防止重复接收。源 ACK 后崩溃从接收记录恢复；checkpoint 和投递标记防止重复追加上下文。压缩保留投递水位，不依赖原始信件正文是否仍在当前窗口。恢复仍沿用原副作用与工具执行记录，不因为消息重投而重放已完成工具。

前台委派因为来信提前返回时，子任务由协作服务继续持有，并仍属于父 run 的完成依赖。后台任务保留原后台语义。子任务的预算保留、结算和释放由 attempt ledger 管理；提前返回的工具用量只供展示，不得再次累加。

## 客户端诊断

inline、fullscreen、JSONL 和 stdio 共用现有 `context_updated` 事件及可选 `data.mailbox`。事件仍是非终态、非耐久审计的状态快照，JSONL schema 保持 3。只含信箱数据的事件不清空上下文 token 计数，也不把“等待审批”显示成“正在思考”。

公开信箱诊断仅允许非负计数、有限非负时长、布尔状态和已知唤醒原因：

| 字段 | 含义 |
| --- | --- |
| `pending_count` / `pending_bytes` | 当前报告的待处理数量与正文大小 |
| `receiver_active` / `has_more` | 接收运行时是否活跃、是否还有积压 |
| `wake_reason` | 来信、可靠接收、上下文投递、任务结束、超时、取消或关闭 |
| `query_count` / `empty_read_count` | 查询和空读次数 |
| `ack_retry_count` / `deduplicated_count` | ACK 重试和重复接收次数 |
| `received_count` / `delivered_count` | 可靠接收和上下文投递数量 |
| `notification_latency_ms` | 提交到通知的延迟 |
| `receipt_latency_ms` / `delivery_latency_ms` | 可靠接收、上下文投递阶段的延迟 |

客户端不会从该诊断字段输出正文、任意发送者描述或错误堆栈。不可用的指标可以省略，不能把缺失的测量报告为实际零。通知延迟不能代替模型看到消息的延迟；长工具、模型请求和审批都可能延后安全投递。

## 兼容与回退

workspace schema 22 添加明确地址及接收端投递记录，通过现有 backup-first 事务升级。portable archive 与 session export 为 9，旧支持版本继续可读。旧消息仅在身份确定时回填地址；缺失接收历史不伪造 ACK 或投递完成。Memory schema 6、config 14、JSONL schema 3 和权限默认值不变。

归档导入、branch 和 rewind 保留历史关系，不因导入待处理信件自动启动模型。当前导入信件标记为 suspended、未投递接收记录标记为 historical；归档信件重新激活尚未接入 follow-up/resume，因此不要依赖显式恢复自动投递这些导入信件。普通运行恢复仍要经过任务归属、权限、契约及副作用恢复检查。回退旧二进制前，恢复对应升级前的数据库备份；不要让旧二进制直接打开新 schema。

## 性能验证

在普通磁盘目录运行：

```bash
python3 scripts/benchmark_mailbox.py \
  --directory /path/to/ordinary-disk \
  --history-rows 1000000 --pending-rows 10000 --iterations 100
```

脚本创建并清理独立临时数据库，不打开用户工作区数据库，不调用付费模型。它使用生产 schema、仓库读取 API 和通知注册表，报告有界批次大小、真实查询计划、读取时长与写次数、Python 峰值分配、提交后空闲等待者被通知的 P95。100 ms 是通知 P95 的观察目标，超标如实输出，不作为受机器负载影响的 CI 硬断言。

重复查询可能命中操作系统缓存；读取计时包含 Python 分配追踪开销。通知计时从已提交的 `send_mailbox` 返回开始，不包含 SQL 提交或模型处理时间。文件系统类型由运行者选择目录决定，脚本不会把内存文件系统宣称为普通磁盘。CI 使用小数据集验证查询走索引、读操作不写库、32/64 KiB 边界及优先配额；百万级结果单独报告。
